# Conformance-корпус SmartApp DSL

Один корпус — два независимых движка. Эти фикстуры прогоняются **и** плагином
IDEA (`SmartAppConformanceTest`), **и** расширением VS Code
(`test/conformance/conformance.test.ts` поверх ядра, а кейсы с диапазонами — ещё
и на уровне провайдеров). Расхождение алгоритмов ловится только здесь: общий
`rules.json` фиксирует данные, а поведение фиксирует этот корпус.

## Раскладка

```text
shared/fixtures/<case>/
  files/<путь в проекте>          # например files/static/references/forms/forms.json
  expected.json                   # ожидаемое поведение
```

Пути внутри `files/` — это пути в тестовом проекте, поэтому они обязаны
содержать `static/references/<вид>/`, иначе файл не считается DSL-файлом.

## Формат `expected.json`

```jsonc
{
  "description": "человекочитаемое описание кейса",

  // Go to Definition. Позиция каретки задаётся якорем, а не смещением:
  // индекс подстроки anchor в файле плюс anchorOffset. Так кейс не ломается от
  // переформатирования фикстуры.
  "definitions": [
    {
      "file": "static/references/scenarios/main.json",
      "anchor": "\"hello_form\"",
      "anchorOffset": 2,
      "targets": [
        {
          "file": "static/references/forms/forms.json",
          "name": "hello_form",
          "ordinal": 0,       // номер среди одноимённых ключей файла
          "line": 1,          // строка определения (0-based)
          "column": 2,        // символ в строке; обязателен, если такой текст
                              // встречается в строке дважды — иначе ожидание
                              // не различает два одинаковых имени
          "rangeText": "\"hello_form\""   // текст под диапазоном
        }
      ]
    }
  ],

  // Find References от позиции каретки. includeDeclaration по умолчанию false.
  // rangeText — само имя, без кавычек: ссылка живёт в rangeInElement литерала,
  // и именно её подсвечивает Find Usages. Диагностика, наоборот, покрывает
  // литерал целиком (там rangeText с кавычками).
  "references": [
    { "file": "...", "anchor": "...", "anchorOffset": 0, "includeDeclaration": false,
      "targets": [ { "file": "...", "line": 3, "rangeText": "name" } ] }
  ],

  // Переименование от позиции каретки: перечисляются места, где имя изменится.
  "rename": [
    { "file": "...", "anchor": "...", "anchorOffset": 0, "newName": "...",
      "edits": [ { "file": "...", "line": 1, "rangeText": "старое_имя" } ] }
  ],

  // Предупреждения файла целиком, в порядке смещений.
  "diagnostics": [
    { "file": "...", "items": [ { "message": "…", "line": 2, "rangeText": "\"missing\"" } ] }
  ],

  // Автодополнение в позиции каретки. items — варианты, которые обязаны быть
  // предложены; absent — которых быть не должно; kind — вид вариантов, и его
  // проверяют оба раннера (в расширении это поле результата, в IDEA — пометка
  // на самом lookup-элементе, `SmartAppCompletionKind`). Без вида «поле» и
  // «имя сущности» с одинаковой меткой означали бы разное, а прогон оставался
  // бы зелёным. Каретку ставьте туда, где
  // префикс пуст (сразу после открывающей кавычки, сразу после точки): при
  // непустом префиксе IDEA часто остаётся с единственным подходящим вариантом
  // и вставляет его сразу, не показывая lookup, — раннер это учитывает, но
  // кейс становится проверкой авто-вставки, а не состава списка. Ни полный
  // список, ни порядок не фиксируются: JSON-плагин IDEA подмешивает свои
  // предложения, а порядок задаёт сортировщик lookup'а платформы — это не
  // часть нашего контракта.
  "completion": [
    { "file": "...", "anchor": "...", "anchorOffset": 0, "kind": "field",
      "items": ["name"], "absent": ["odd.field"] }
  ],

  // Семантические токены файла: только перечисленные типы, в порядке смещений.
  "semanticTokens": [
    { "file": "...", "type": "smartappJinjaVariable",
      "texts": ["main_form", "name"], "lines": [3, 3] }
  ],

  // Имена, попавшие в индекс определений (проверка строгости индексации).
  "indexedNames": [ { "kind": "FORM", "names": ["hello_form"] } ]
}
```

Все секции необязательны: кейс проверяет только то, что перечислил. Пустой
массив — осмысленное ожидание («ничего не найдено»), поэтому его отличают от
отсутствующей секции.

Секция, которую раннер не умеет проверять, — это молчаливо непроверенный
контракт. Поэтому оба раннера падают на неизвестной секции: добавляя новую,
реализуйте её сразу с обеих сторон (`SUPPORTED_SECTIONS` в
`SmartAppConformanceTest`).
