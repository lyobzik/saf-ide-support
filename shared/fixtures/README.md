# Conformance-корпус SmartApp DSL

Один корпус — два независимых движка. Эти фикстуры прогоняются **и** плагином
IDEA (`SmartAppConformanceTest`), **и** расширением VS Code
(`test/conformance/conformance.test.ts` поверх ядра, а кейсы с диапазонами — ещё
и на уровне провайдеров). Расхождение алгоритмов ловится только здесь: общий
`rules.json` фиксирует данные, а поведение фиксирует этот корпус.

## Раскладка

```text
shared/fixtures/<case>/
  files/<путь в проекте>          # например files/static/references/forms/forms.json
  expected.json                   # ожидаемое поведение
```

Пути внутри `files/` — это пути в тестовом проекте, поэтому они обязаны
содержать `static/references/<вид>/`, иначе файл не считается DSL-файлом.

Исключение — **ресурсы приложения**: `app_config.py` и модули, на которые ведёт
`RESOURCES`, лежат рядом с набором (`files/app_config.py`,
`files/app/resources/…`), и корень приложения — это каталог, содержащий
`static/references`. Такие файлы читают обе стороны: плагин добавляет их в
тестовый проект, ядро расширения — в индекс через `upsert`. Каретку в `.py`
ставить нельзя: без плагина Python это plain text, и элемента нужного вида в
тестовой платформе не существует.

**Объявление ключевого слова, зарегистрированного приложением, — строка
регистрации в Python.** Поэтому в секции `references` при
`"includeDeclaration": true` в `targets` перечисляется не свойство JSON под
кареткой, а `actions["<имя>"]` в файле ресурсов. Обе реализации отдают именно
её: ядро — из `referencesAt`, плагин — из
`SmartAppCustomKeywordTargets.of(...).declarations`.

## Формат `expected.json`

```jsonc
{
  "description": "человекочитаемое описание кейса",

  // Go to Definition. Позиция каретки задаётся якорем, а не смещением:
  // индекс подстроки anchor в файле плюс anchorOffset. Так кейс не ломается от
  // переформатирования фикстуры.
  "definitions": [
    {
      "file": "static/references/scenarios/main.json",
      "anchor": "\"hello_form\"",
      "anchorOffset": 2,
      "targets": [
        {
          "file": "static/references/forms/forms.json",
          "name": "hello_form",
          "ordinal": 0,       // номер среди одноимённых ключей файла
          "line": 1,          // строка определения (0-based)
          "column": 2,        // символ в строке; обязателен, если такой текст
                              // встречается в строке дважды — иначе ожидание
                              // не различает два одинаковых имени
          "rangeText": "\"hello_form\""   // текст под диапазоном
        }
      ]
    }
  ],

  // Find References от позиции каретки. includeDeclaration по умолчанию false.
  // rangeText — само имя, без кавычек: ссылка живёт в rangeInElement литерала,
  // и именно её подсвечивает Find Usages. Диагностика, наоборот, покрывает
  // литерал целиком (там rangeText с кавычками).
  "references": [
    { "file": "...", "anchor": "...", "anchorOffset": 0, "includeDeclaration": false,
      "targets": [ { "file": "...", "line": 3, "rangeText": "name" } ] }
  ],

  // Переименование от позиции каретки: перечисляются места, где имя изменится.
  "rename": [
    { "file": "...", "anchor": "...", "anchorOffset": 0, "newName": "...",
      "edits": [ { "file": "...", "line": 1, "rangeText": "старое_имя" } ] }
  ],

  // Предупреждения файла целиком, в порядке смещений.
  "diagnostics": [
    { "file": "...", "items": [ { "message": "…", "line": 2, "rangeText": "\"missing\"" } ] }
  ],

  // Автодополнение в позиции каретки. items — варианты, которые обязаны быть
  // предложены; absent — которых быть не должно; kind — вид вариантов, и его
  // проверяют оба раннера (в расширении это поле результата, в IDEA — пометка
  // на самом lookup-элементе, `SmartAppCompletionKind`). Без вида «поле» и
  // «имя сущности» с одинаковой меткой означали бы разное, а прогон оставался
  // бы зелёным. Каретку ставьте туда, где
  // префикс пуст (сразу после открывающей кавычки, сразу после точки): при
  // непустом префиксе IDEA часто остаётся с единственным подходящим вариантом
  // и вставляет его сразу, не показывая lookup, — раннер это учитывает, но
  // кейс становится проверкой авто-вставки, а не состава списка. Ни полный
  // список, ни порядок не фиксируются: JSON-плагин IDEA подмешивает свои
  // предложения, а порядок задаёт сортировщик lookup'а платформы — это не
  // часть нашего контракта.
  "completion": [
    { "file": "...", "anchor": "...", "anchorOffset": 0, "kind": "field",
      "items": ["name"], "absent": ["odd.field"] }
  ],

  // Семантические токены файла: только перечисленные типы, в порядке смещений.
  "semanticTokens": [
    { "file": "...", "type": "smartappJinjaVariable",
      "texts": ["main_form", "name"], "lines": [3, 3] }
  ],

  // Имена, попавшие в индекс определений (проверка строгости индексации).
  "indexedNames": [ { "kind": "FORM", "names": ["hello_form"] } ],

  // Словарь ключевых слов, зарегистрированных приложением. Приложение задаётся
  // любым его DSL-файлом — каретка и PSI для этой секции не нужны, обе стороны
  // отдают словарь из своего резолвера.
  "customKeywords": [
    {
      "file": "app_a/static/references/actions/actions.json",
      "items": [
        {
          "category": "action",
          "name": "shared",
          // Место ДЕЙСТВУЮЩЕЙ регистрации: у затенённой пары это файл
          // производного класса, а не базового.
          "registration": {
            "file": "app_a/app/resources/custom_app_resources.py",
            "line": 9, "column": 17, "rangeText": "shared"
          }
        }
      ]
    }
  ],

  // Словарь модели пользователя: имена, доступные в Jinja как `<корень>.<имя>`.
  // Приложение задаётся любым его DSL-файлом — каретка для секции не нужна.
  "userFields": [
    {
      "file": "app_a/static/references/behaviors/behaviors.json",
      "enabled": true,            // собран ли словарь вообще; false и пустой
                                  // items — разные вещи
      "rootVariables": ["user"],  // имена, под которыми модель доступна: их
                                  // может быть несколько (один self._user
                                  // связан с несколькими ключами) либо ноль
                                  // (найдено доказательство обратного)
      "diagnosticsEnabled": true, // разрешён ли WARNING
      "items": [
        { "origin": "field", "name": "my_field",
          "declaration": { "file": "app_a/app/user/user.py", "line": 9,
                           "column": 40, "rangeText": "my_field" } },
        { "origin": "snapshot", "name": "variables" }   // объявления нет
      ]
    }
  ]
}
```

Правила секции `userFields`:

- **запись на каждое объявление**, а не на имя: у имени, объявленного и списком
  `fields`, и `self.<имя>` в `__init__`, записей две — с разными `origin`
  (`field`, `self`, `def`, `class`) и разными `declaration`;
- **`declaration` отсутствует ровно у `origin: "snapshot"`** — у имени из
  снимка фреймворка строки в коде проекта нет. Раннеры это проверяют, а не
  пропускают: запись `snapshot` с `declaration` (и наоборот) роняет кейс;
- **сравнение полное и по множеству**: перечисляются все имена словаря, иначе
  лишнее никто не заметит, а порядок задаёт обход и контрактом не является;
- `enabled: false` — словаря нет вовсе (цепочка `USER` недействительна);
  `rootVariables: []` — есть доказательство обратного, и под дефолтным именем
  семантики нет; `diagnosticsEnabled` держится на двух условиях сразу —
  полнота словаря и доказанная привязка корня.

Порядок **целей перехода** (секция `definitions`), в отличие от порядка записей
`userFields`, зафиксирован: пара «файл + смещение начала», по ней же идёт
дедупликация. Оба резолвера сортируют перед выдачей.

Правила секции `customKeywords`:

- **порядок не фиксируется**: раннеры сортируют по паре `(category, name)` —
  порядок задаёт обход цепочки, а не контракт;
- **сравнение полное**: перечисляются все слова приложения, иначе лишнее слово
  никто не заметит. `"items": []` — осмысленное ожидание «словарь пуст»
  (условный `RESOURCES`, неизвестная база), и это не то же самое, что
  отсутствующая запись;
- **затенение проверяется здесь же**: `registration` указывает на производный
  класс, поэтому объединение цепочки вместо свёртки по `super()` сразу красит
  кейс.

Все секции необязательны: кейс проверяет только то, что перечислил. Пустой
массив — осмысленное ожидание («ничего не найдено»), поэтому его отличают от
отсутствующей секции.

Секция, которую раннер не умеет проверять, — это молчаливо непроверенный
контракт. Поэтому оба раннера падают на неизвестной секции: добавляя новую,
реализуйте её сразу с обеих сторон (`SUPPORTED_SECTIONS` в
`SmartAppConformanceTest`).

## Что корпус не проверяет

- **Уровень адаптера VS Code.** Кейсы проходят плагин IDEA и **ядро**
  расширения; раннера поверх `src/vscode/**` нет ни для одной фикстуры.
  Трансляцию смещений в `Position`, `Uri`, диапазоны `CompletionItem` и
  содержимое `WorkspaceEdit` закрывают точечные тесты `test/vscode/**`. Пункт
  в бэклоге.
- **Позиции, где реализации расходятся осознанно.** Такой кейс в корпус не
  пишется: любое ожидание красит одну из сторон. Сегодня это Find Usages по
  имени модели пользователя, у которого нет объявления в приложении (в IDEA
  цели не существует, и действие недоступно; в VS Code имя известно от позиции
  каретки, и вхождения возвращаются), отказ переименования и направление
  «каретка в `.py`». Каждое такое расхождение обязано быть в бэклоге и в
  `AGENTS.md`, а проверяться — юнит-тестами каждой стороны.
