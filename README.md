# SmartApp DSL — поддержка в IntelliJ IDEA и VS Code

Репозиторий содержит **две** реализации поддержки одного языка: плагин для
IntelliJ-платформы (`idea-plugin/`) и расширение для VS Code
(`vscode-extension/`). Обе понимают одну и ту же семантику и держатся вместе
общими контрактами из `shared/` — подробнее в разделе «Монорепозиторий».

Плагин добавляет поддержку DSL-сценариев фреймворка **Sber SmartApp Framework**
(`smart_app_framework`) прямо в IDE. Сценарии этого фреймворка описываются не
отдельным языком, а **JSON-файлами** в каталоге `static/references/` (подкаталоги
`scenarios/`, `forms/`, `actions/`, `behaviors/`, `field_fillers/`,
`classifiers/`). Плагин понимает их семантику и помогает с навигацией и
редактированием.

## Возможности

- **Подсветка** ключевых слов (значения поля `type`) и структурных ключей.
- **Переход к определению** сущности — Go to Definition / Ctrl+Click (⌘+Click).
- **Поиск использований** — Find Usages / Alt+F7.
- **Автодополнение** значений `type` и ссылочных ключей (`form`, `scenario`,
  `filler`, `classifier`, `action`).
- **Предупреждения** о неразрешённых ссылках (severity WARNING — не ошибка, так
  как целевая сущность может быть ещё не создана).
- **Поля форм в Jinja** — навигация, автодополнение и подсветка разметки в
  выражениях `{{ main_form.<field> }}` и `{% … %}` (подробнее ниже).
- **Ключевые слова самого приложения** — те, что навык регистрирует в своём
  Python-коде: подсветка, автодополнение, переход к строке регистрации и поиск
  использований (подробнее ниже).
- **Поля модели пользователя в Jinja** — `{{ user.<field> }}`: автодополнение
  имён, переход к строке объявления в Python-коде навыка, поиск использований и
  предупреждение о несуществующем имени (подробнее ниже).
- **Переход к файлу шаблона** — `"file"` при `"type": "unified_template"` ведёт
  в `static/references/templates/<значение>`; в этой же позиции предлагаются
  имена файлов каталога шаблонов, вложенные — вместе с путём. Путь
  регистрозависим: `Items.JINJA2` при файле `items.jinja2` целью не является.

Ни плагин, ни расширение не вводят собственный язык или лексер: оба строят
семантический слой поверх встроенного JSON-парсера редактора. Плагин работает в
любой IDE на платформе IntelliJ, где есть бандл-плагин JSON (IDEA
Community/Ultimate, PyCharm, GIGA IDE и др.); расширение — в VS Code 1.90+.

## Установка

Ни плагин, ни расширение пока не публикуются в Marketplace — обе стороны
ставятся из файла:

```text
smartapp-dsl-<версия>.zip     # плагин для IntelliJ-платформы
smartapp-dsl-<версия>.vsix    # расширение для VS Code
```

Собирать необязательно: готовые артефакты лежат в
[Releases на GitHub](https://github.com/lyobzik/saf-ide-support/releases) —
скачиваются без аккаунта. Участникам проекта в GitLab те же файлы доступны в
реестре пакетов. Как они туда попадают — в разделе
[CI/CD](#cicd-два-хостинга-один-набор-проверок); коротко: по тегу вида
`v<версия>` сборка идёт автоматически, а версия в теге обязана совпадать с
версией в манифестах.

Сборка из исходников нужна, только если хочется поставить версию, которой ещё
нет в релизах, — тогда `tools/package.sh` кладёт оба файла в `dist/`; о том, что
внутри, — в разделе [Сборка из исходников](#сборка-из-исходников).

### Плагин для IDE на IntelliJ-платформе

1. **Settings/Preferences → Plugins**.
2. Иконка шестерёнки ⚙ → **Install Plugin from Disk…**.
3. Выберите ZIP-файл.
4. Перезапустите IDE по запросу.

### Расширение для VS Code

```bash
code --install-extension dist/smartapp-dsl-<версия>.vsix
```

Либо **Extensions → … → Install from VSIX…**.

После перезапуска откройте проект, содержащий каталог `static/references/…`, —
подсветка, переход к определению, поиск использований и автодополнение заработают
в JSON-файлах внутри этого каталога.

> Минимальная версия платформы: build **251** (IDEA 2025.1) и новее.

## Как это работает

Разделы ниже нужны, только если интересно, по каким правилам работает
семантика: для установки и обычного использования их читать не обязательно.

### Поля форм в Jinja-значениях

Строковые значения DSL часто содержат Jinja2-шаблоны. Внутри выражений Jinja —
и в интерполяциях `{{ … }}`, и в statement-тегах `{% … %}` — плагин понимает
обращения к полям формы:

```json
"greeting": "{{ main_form.name }}"
```

- **Go to Definition / Find Usages** для имени поля — ведут на определение поля
  в `forms.<форма>.fields.<поле>`. Целевая форма в сценарии берётся из свойства
  `form` того же сценария, а внутри файла формы `main_form` — это сама форма,
  в определении которой стоит значение.
- **Переход с самой переменной `main_form`** — на определение целевой формы.
  Имени формы в этом месте не написано, поэтому переименование формы `main_form`
  не переписывает и в поиск использований формы он не попадает.
- **Автодополнение** имён полей после `{{ main_form.` — из индекса полей
  целевой формы (предлагаются только имена-идентификаторы), а на месте самого
  идентификатора (`{% if mai`) предлагается переменная `main_form` с подписью —
  именем целевой формы.
- **Подсветка разметки** Jinja: разделители, переменные, `.`, фильтры (`|` и имя),
  строковые литералы — настраивается в Settings → Color Scheme → SmartApp DSL.
- **WARNING** «Не удаётся разрешить поле» — только когда форма известна
  (статическая строка в `form`), а поля в ней нет. Динамический выбор формы
  (`"form": "{{ … }}"`) предупреждений не даёт.

Осознанные ограничения текущей версии: у цепочки `main_form.a.b` семантику
получает только первый сегмент — что такое `b`, знать неоткуда, схемы значений
полей не существует; `main_form` в позиции чужого поля (`variables.main_form.x`)
семантики не получает вовсе; поля, чьи имена не являются идентификаторами
(содержат `.`, `:`, `-`), в автодополнении не предлагаются. Jinja работает и в
строковых элементах JSON-массивов, не только в значениях свойств.

### Шаблоны в отдельных файлах

Значение `"file"` в объекте `"type": "unified_template"` называет файл шаблона:

```json
"items": { "type": "unified_template", "file": "items.jinja2", "loader": "json" }
```

Такое значение — ссылка на файл `static/references/templates/items.jinja2` того
же набора: работает переход, а отсутствующий файл даёт WARNING. Значение
содержит имя файла вместе с расширением; вложенные пути (`nested/items.jinja2`)
допускаются, а выход за пределы каталога (`../…`) целью не считается и ошибкой
не помечается.

Правило выведено из раскладки эталонного приложения, а не из исходников
`smart_app_framework`: ключа `file` в публичных исходниках фреймворка нет.

**Подсветка внутри самих `.jinja2`-файлов не входит в задачу плагина.** Обе
реализации — семантический слой поверх JSON-парсера редактора, отдельный язык
они не вводят; раскрасить сам шаблон помогут специализированные средства (в
VS Code — любое расширение для Jinja, в IDE на платформе IntelliJ — плагин с
поддержкой Jinja2). Переход в файл при этом работает независимо от них.

### Ключевые слова, зарегистрированные приложением

Словарь `type` — не только свойство фреймворка: навык добавляет свои действия,
требования и филлеры сам. Делается это в подклассе `SmartAppResources`, а
активный класс назначает `app_config.py`:

```python
# app/resources/custom_app_resources.py
class CustomAppResources(SmartAppResources):
    def init_actions(self):
        super().init_actions()
        actions["custom_action"] = CustomAction

# app_config.py
RESOURCES = CustomAppResources
```

После этого `"type": "custom_action"` в JSON приложения — такое же ключевое
слово, как фреймворковое: оно подсвечивается, предлагается в автодополнении (с
подписью — именем класса, потому что больше в значении `type` о нём ничего не
видно), по Ctrl+Click ведёт **на строку регистрации** в Python-файле, а Alt+F7 /
Shift+F12 показывает его вхождения по всем DSL-файлам приложения.

Приложение — это каталог, внутри которого лежит `static/references`. Отсюда
границы: соседнее приложение чужих слов не видит, вложенное (`subapp`) — тоже
самостоятельное. Каталоги зависимостей и сборки (`venv`, `.venv`,
`site-packages`, `__pycache__`, `node_modules`, `build`, `dist`) исключены из
разбора Python-кода и из вхождений кастомного слова — но **только из них**:
обычные DSL-файлы внутри таких каталогов по-прежнему индексируются и участвуют
в резолве ссылок между сущностями, как и раньше. Это известное ограничение, оно
записано в бэклоге.

Цепочка наследования разрешается по правилам Python: регистрации базового
класса учитываются, **только** если производный метод вызвал `super()`, а при
совпадении имени побеждает производный класс — он же становится целью перехода.
Осознанные ограничения версии 1:

- **одиночное наследование**: любая множественная база (в том числе безобидный
  на вид `class C(AppBase, LoggingMixin)`) отключает разбор для этого
  приложения целиком — библиотечный миксин сканеру не виден, но участвует в
  MRO, и догадка показывала бы слова, которых в рантайме нет;
- **статические регистрации**: `actions["x"] = C` и `actions.update({...})` с
  литеральными ключами; вычисляемые имена (f-строки, конкатенация, циклы)
  пропускаются молча;
- `super()` и импорты распознаются **текстово**: вызов через переменную или
  относительный импорт (`from .x import Y`) не будет замечен, и слова просто не
  появятся;
- **переименование не поддерживается**: имя живёт и в Python, и во всех JSON,
  согласованно переписать их плагин не берётся;
- **диагностики «неизвестный `type`» нет**: словарь заведомо неполон, WARNING
  давал бы ложные срабатывания.

Обратное направление — Alt+F7 в `.py` — работает в двух местах: **на самой
строке регистрации** и **на классе**, который в ней указан. Во втором случае
вхождения из DSL добавляются к обычному поиску использований класса, а не
заменяют его: в одном окне и ссылки на класс в Python-коде, и строки DSL, где
стоит его слово.

Границы этого направления:

- нужен **плагин Python**: без него `.py` для IDE — обычный текст, класса под
  кареткой не существует, и различить в файле регистрацию нечем (в GIGA IDE
  плагин есть);
- класс со словом сопоставляется **по имени**, импорты для правой части
  регистрации не разрешаются: два одноимённых класса из разных модулей одного
  приложения неразличимы, и Alt+F7 на любом покажет вхождения обоих слов;
- классы из исключённых каталогов (`venv`, `site-packages`, …) вхождений не
  получают — как и JSON-файлы оттуда;
- **в VS Code направления нет вовсе**: провайдеры расширения зарегистрированы
  для JSON, и в `.py` редактор их не спрашивает. Это осознанное расхождение
  реализаций, в общий корпус оно не пишется.

### Модель пользователя в Jinja

Шаблон видит не только форму: параметризатор кладёт в его параметры объект
пользователя, и обращения вида `{{ user.smart_geo }}` встречаются в боевых
наборах. Обе реализации собирают словарь его имён и дают по нему навигацию,
автодополнение, поиск использований и предупреждения.

Словарь складывается из двух половин. **Пол** — снимок полей фреймворка
(`shared/keywords/user_fields.json`, генерируется из вендоренных исходников):
без него типовой навык не получил бы ничего, потому что его класс пользователя
обычно выглядит так:

```python
# app/user/user.py
class CustomUser(User):
    @property
    def fields(self):
        return super().fields + [Field("smart_geo", Geo)]

# app_config.py
USER = CustomUser
```

**Половина приложения** — то, что добавил сам навык: элементы списка `fields`,
присваивания `self.<имя>` в методах, `def <имя>` и имена уровня класса. Голая
аннотация (`smart_geo: Geo` без значения) объявлением не считается — атрибута
она не создаёт. Ctrl+Click на имени ведёт **на строку объявления** в Python, и
целей может быть несколько: одно имя нередко объявлено и списком `fields`, и
`self.<имя>` в `__init__`. У имени из снимка фреймворка объявления нет —
переходить некуда, и это не ошибка.

**Корневое имя не зашито.** `user` — не гарантия фреймворка: параметры шаблона
собирает `Parametrizer._get_user_data`, и библиотечный кладёт туда `message`,
`forms`, `variables`, но не самого пользователя. Имя появляется, только когда
навык дописал его в своём параметризаторе:

```python
# app/user/parametrizer.py
class CustomParametrizer(Parametrizer):
    def _get_user_data(self, text_preprocessing_result=None):
        data = super()._get_user_data(text_preprocessing_result)
        data["user"] = self._user
        return data

# app_config.py
PARAMETRIZER = CustomParametrizer
```

Обе реализации это читают. Имён может быть несколько (один `self._user`,
связанный с двумя ключами, — два равноправных корня). Пока привязка не
доказана разбором, работают **предложения** — автодополнение, переход, поиск
использований — под именем `user`, но не **утверждения**: WARNING остаётся
выключенным. Это осознанная асимметрия: подчёркивать имя под корнем, которого
может не быть, значит выдумывать ошибку.

WARNING «Не удаётся разрешить поле … модели пользователя» включается при двух
условиях сразу: словарь полон (в цепочке классов не сработал ни один гаситель
вроде `__getattr__`, `setattr(`, `__slots__`, метакласса или декоратора на
классе) **и** корневое имя доказано. На эталонном приложении, где
`_get_user_data` только вызывает `super()`, диагностики не будет — это
ожидаемый результат, а не дефект.

Осознанные ограничения версии 1:

- **семантику получает только первый сегмент**: в `{{ user.variables.smart_geo }}`
  это `variables`; хвост — атрибут значения, объявления которому в
  `static/references/` нет. По той же причине там не ставится WARNING;
- **переименование не поддерживается** — имя живёт и в Python, и во всех JSON;
- **Alt+F7 по имени из снимка фреймворка в IDEA недоступен**: платформа ищет
  использования от цели, а у такого имени цели не существует. В VS Code поиск
  идёт от позиции каретки, поэтому вхождения там возвращаются. Расхождение
  осознанное и записано в бэклоге;
- **Alt+F7 на самом классе пользователя не заводится**: в тексте DSL стоит
  псевдоним из параметризатора, а не имя класса.

## Монорепозиторий: две реализации и общий контракт

```text
idea-plugin/        # плагин для IntelliJ-платформы (Kotlin, Gradle)
vscode-extension/   # расширение для VS Code (TypeScript, npm)
shared/
  rules/rules.json      # контракт данных: виды, каталоги, правила ссылок, ключи
  keywords/keywords.json  # словарь ключевых слов фреймворка
  fixtures/             # conformance-корпус: общий для обеих реализаций
tools/                # генератор словаря
```

Системы сборки намеренно не объединены: Gradle собирает плагин, npm — расширение.
Вместе их держат два контракта:

- **данные** — `shared/rules/rules.json` генерируется из Kotlin-таблиц плагина
  (`./gradlew :idea-plugin:exportRules`) и читается расширением; править его
  руками нельзя, `exportRules --check` следит за актуальностью снимка;
- **поведение** — `shared/fixtures/` прогоняются и тестами плагина
  (`SmartAppConformanceTest`), и тестами расширения. Расхождение алгоритмов
  ловится только так, поэтому новая семантика без нового кейса не принимается.

Оба контракта проверяются в CI — см. следующий раздел.

## CI/CD: два хостинга, один набор проверок

Проверки описаны один раз в `tools/ci/` и вызываются обоими хостингами, поэтому
разойтись они не могут: в YAML нет ни одной команды сборки или проверки, только
вызовы этих скриптов.

| Файл | Что в нём |
|---|---|
| `tools/ci/run.sh <шаг>…` | сборка, проверки, упаковка — то, что запускается и локально |
| `tools/ci/deps-debian.sh` | системные пакеты для интеграционного теста в голом Debian-образе |
| `tools/ci/publish_gitlab.py` | реестр пакетов и Release — всё, что знает про API GitLab |
| `tools/ci/publish_github.py` | Release с ассетами — всё, что знает про API GitHub |

Любой шаг воспроизводится на машине разработчика той же строкой, что в CI:

```bash
tools/ci/run.sh contract:keywords contract:schema test:vscode
```

Для шагов со стороны IDEA локально удобнее собирать против установленной IDE:
`GRADLE_ARGS= tools/ci/run.sh test:idea` (по умолчанию платформа берётся из
maven, потому что на runner'ах установленной IDE нет).

**GitLab — основной хостинг.** Полный пайплайн: контракты, тесты обеих сторон,
`verifyPlugin`, упаковка и релиз. Пайплайн создаётся на merge request, на
`master`, на релизном теге `v<версия>` и по ручному запуску; ветка без MR
пайплайна не создаёт.

**GitHub — публичный репозиторий и вторая площадка релиза.** Там идут
контракты, тесты плагина с `verifyPlugin` и юнит-сторона расширения, а по тегу
собираются оба артефакта и создаётся Release. Минуты стандартных runner'ов на
публичных репозиториях бесплатны, поэтому урезать проверки незачем — публикуем
только то, что сами проверили. Не запускается там лишь интеграционный тест VS
Code: ему нужны системные библиотеки Electron, а один проверенный способ их
поставить лучше двух похожих (этим занят GitLab на каждом пайплайне). Фильтр
тегов — `v[0-9]+.[0-9]+.[0-9]+` (у GitLab то же самое регулярным выражением);
на синтаксис фильтров полагаться нельзя, поэтому релизным тег окончательно
делает проверка `contract:version`, идущая на обоих хостингах.

**Один тег — две публикации, у них разные адресаты.** GitHub кладёт файлы в
Release, откуда их скачивают **анонимно**; GitLab кладёт их в реестр пакетов
приватного проекта — для участников. Артефакты на обеих площадках собраны из
одного коммита одними и теми же командами (`tools/ci/run.sh package:*`), но
**не побайтово одинаковы**: упаковка не воспроизводима — два прогона дают
файлы одного размера с разными SHA-256. Сравнивать хеши между площадками
бессмысленно; сравнивать имеет смысл версию и происхождение. Право на запись у
GitHub-стороны выдано только job'у релиза (`permissions: contents: write`) и
только по тегу.

**Модель угроз узкая, и это записано намеренно.** Доверенными считаются все, у
кого есть право записи в репозиторий: роль Write позволяет создавать и
редактировать Releases напрямую, без всякого CI. Отделить публикацию от такого
участника внутри одного репозитория технически невозможно, поэтому пайплайн и
не притворяется, что защищает от него. Он защищает от случайностей: обрыва
между загрузками, гонок, наполовину опубликованного релиза, несовпадения
артефактов с уже выложенными, повторного запуска, переставленного тега — и от
подмены после выпуска. Пересмотреть придётся до того, как право записи получит
человек или бот, которому нельзя доверить публикацию: тогда Releases уносятся в
отдельный репозиторий со своим списком писателей.

**Перед первым релизом нужны две настройки репозитория.**

*Среда `release` с required reviewers* (Settings → Environments) — предохранитель
штатного процесса: релиз не уедет от случайно поставленного тега, пока человек
не подтвердит. Границей безопасности она не является (см. выше).

*Immutable releases.* Без них опубликованный релиз можно подменить, и сверка
digest при публикации перестаёт что-либо гарантировать после неё. Проверка
возможна только по результату: скрипт падает, если опубликованный релиз оказался
изменяемым. Зелёного релиза без настройки не бывает, но первый такой релиз
успеет стать публичным — поэтому включать нужно заранее.

Полезно, но не обязательно: *ruleset на теги `v*`* с исключением для того, кто
выпускает релизы, — он не даёт поставить релизный тег случайно.

**Релиз в GitLab** — по защищённому тегу `v<версия>`; защита
тега обязательна и проверяется самим релизным job'ом: он читает список
защищённых тегов по API и отказывается публиковать, если тег не покрыт или
список прочитать не удалось. Для чтения нужен project access token с областью
`read_api` в переменной `SMARTAPP_API_TOKEN` — job-токен к этому эндпоинту не
допускают. У переменной обязаны стоять флаги «Protect variable» и «Mask
variable», а **область видимости — `release`, а не `*`**: со звёздочкой токен
приходил бы в каждый job пайплайна, включая тесты, которые исполняют чужой код
(зависимости npm и плагины Gradle). Ради этой области у релизного job'а и у
`release:smoke` объявлен `environment: name: release`. Артефакты
загружаются в Generic Package Registry, и Release ссылается на них: ссылки
постоянны, в отличие от артефактов джоб, у которых есть срок жизни. Публикация
идемпотентна — повторный запуск после обрыва доводит её до конца либо внятно
отказывает, но второго состояния не создаёт. Проект приватный, поэтому файлы
релиза доступны участникам проекта, а не анонимно.

## Словарь ключевых слов

Список «ключевых слов» (допустимые значения `type`) генерируется из исходников
фреймворка скриптом-генератором, который AST-парсит
`smart_kit/resources/__init__.py`:

```bash
python tools/generate_keywords.py [путь-к-resources__init__.py]
```

Результат — `shared/keywords/keywords.json` (общий для обеих реализаций; в
ресурсы плагина он копируется на этапе сборки). Режим `--check` проверяет, что
закоммиченный словарь соответствует vendored-исходнику. В репозитории лежит
vendored-копия исходника фреймворка (`tools/vendor/`), поэтому генератор можно
запускать без доступа к самому фреймворку. Перезапускайте генерацию при
обновлении версии фреймворка.
