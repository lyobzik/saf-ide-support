# Ключевые слова, зарегистрированные приложением (custom app resources)

> **Статус:** не реализован. Пройдено два раунда ревью: тринадцать
> архитектурных пробелов закрыты решениями ниже. Два изменения переписали план
> целиком: сканируется **не всякий** наследник `SmartAppResources`, а класс,
> назначенный в `app_config.py`; и регистрации из цепочки наследования не
> объединяются, а разрешаются по правилам Python (`super()` + переопределение).

## Как это работает во фреймворке

`SmartAppResources` (`tools/vendor/resources__init__.py:100`) — реестр языка:
методы `init_*` кладут в словари пары «имя из JSON → Python-класс». Приложение
наследует класс и дописывает свои пары, а точку входа назначает `app_config.py`:

```python
# app/resources/custom_app_resources.py
class CustomAppResources(SmartAppResources):
    def init_actions(self):
        super().init_actions()
        actions["custom_action"] = CustomAction

# app_config.py
from app.resources.custom_app_resources import CustomAppResources
RESOURCES = CustomAppResources
```

Происхождение правила: публичных исходников `smart_kit` в окружении нет, но
docstring самого класса в эталонном проекте говорит прямо — «Для использования
данных ресурсов присвойте переменной `RESOURCES` в `app_config` этот класс как
значение». Это фиксируется в контракте так же, как правило `file` для шаблонов.

Вывод: **словарь ключевых слов — свойство приложения**, а `keywords.json` —
снимок только фреймворковой половины.

## Что не работает сейчас (замер)

`static/references/actions/actions.json:27` эталонного проекта содержит
`"type": "custom_action"`. Замер ядра расширения на этом файле:

```
ТОКЕНЫ: []                            # подсветки нет
ВАРИАНТОВ: 42 | custom_action: false  # не предлагается
clear_all_scenarios: true             # фреймворковое слово той же категории — есть
```

Перехода к регистрации и поиска использований нет. Диагностики «неизвестный
`type`» у нас нет вовсе, поэтому ошибка молчаливая.

## 1. Активный ресурсный класс

Сканируется только цепочка классов, достижимая от `RESOURCES`:

1. в корне приложения читается `app_config.py`, из него берётся **безусловное
   присваивание верхнего уровня** `RESOURCES = <Name>` (нулевой отступ, вне
   `if`/`try`/`with`/`def`/`class`). Несколько таких присваиваний — побеждает
   последнее, это и есть семантика Python. Но если присваивание `RESOURCES`
   встречено **не** на верхнем уровне (в ветке `if dev:` и т.п.), приложение
   считается динамическим и кастомных слов нет вовсе — угадывать ветку нельзя,
   а взять верхнеуровневое значение и промахнуться хуже, чем промолчать;
2. в том же файле ищется импорт `<Name>`: `from <a.b.c> import <Name>` (в т.ч.
   `as`-алиас) либо `import <a.b.c>` + `RESOURCES = <a.b.c>.<Name>`;
3. модуль превращается в путь: `a.b.c` → `<appRoot>/a/b/c.py`, а если такого
   файла нет — `<appRoot>/a/b/c/__init__.py`;
4. в найденном файле берётся `class <Name>(<bases>)`, из него — методы
   `init_*`;
5. базы класса, которые резолвятся по тем же правилам в файл **внутри того же
   приложения**, обходятся рекурсивно (глубина ≤ 8, посещённые файлы
   запоминаются). Нерезолвимая база (`SmartAppResources` из библиотеки) —
   конец ветки, это не ошибка.

Чего это стоит и что даёт: неиспользуемый наследник, тестовые ресурсы,
альтернативные классы и ресурсы соседнего приложения в индекс **не попадают**.
Если `RESOURCES` не найден или не резолвится (динамика, вычисляемое значение),
кастомных слов нет — молча, как и везде: догадываться, какой из наследников
«настоящий», хуже, чем не подсказывать.

## 2. Корень приложения

```
referencesRoot   = <appRoot>/static/references     (уже есть в контракте)
applicationRoot  = referencesRoot без paths.rootSegments
```

То есть каталог, содержащий `static`, — в эталонном проекте это корень с
`app/`, `app_config.py` и `static/`. Все пути (`app_config.py`, модули, `.py`)
разрешаются относительно него.

**Вложенные приложения.** Корни могут вкладываться друг в друга
(`project/static/references` и `project/subapp/static/references`), и тогда
рекурсивный обход внешнего захватил бы внутреннее. Правило владения — одно на
обе реализации и на оба вида файлов:

```
appRootOf(file) = ближайший (самый глубокий) каталог-предок D, у которого есть D/static/references
```

Файл принадлежит ровно одному приложению; `.py` внутреннего приложения не
участвует в словаре внешнего, и наоборот. `referencesRoot` уже ищет сегменты с
конца, то есть отдаёт самый глубокий набор, — правило согласовано с ним.

Корректность даёт именно эта проверка равенства (`appRootOf(registration) ==
appRootOf(jsonFile)`), а не область поиска: scope в IDEA лишь сужает перебор.
Кейсы корпуса нужны оба — соседние приложения и вложенные.

## 3. Scope в IDEA

`SmartAppScopes` сегодня отдаёт каталог `references` — Python-файл в него не
входит, поэтому нужен второй scope:

```kotlin
/** Каталог приложения целиком: и static/references, и его Python-файлы. */
fun applicationScope(file: VirtualFile): GlobalSearchScope
```

Реализация — `GlobalSearchScopes.directoryScope(project, applicationRoot, true)`
с пересечением `ProjectScope.getContentScope(project)` (библиотеки и
`site-packages` не наши). Одного content scope мало: виртуальное окружение,
лежащее внутри content root, в него попадает. Поэтому список исключённых
сегментов из контракта применяется в **трёх** местах и одинаково с обеих
сторон: `InputFilter` индекса (файл под исключённым сегментом не индексируется
вовсе), резолвер импортов (в такие каталоги не заходит) и глоб/обработчик
watcher'а в VS Code. Тест на `venv` — обязательный и парный. Соседнее приложение в scope не попадает: его корень —
другой каталог. Вложенное — попадает, поэтому результаты дополнительно
фильтруются правилом владения из раздела 2; scope отвечает за скорость,
фильтр — за корректность. Для JSON-запросов остаётся прежний `forPsiFile`.

## 4. Find Usages и навигация — конкретное API

Полагаться на то, что платформа сама перейдёт от `JsonStringLiteral` к цели
ссылки, нельзя: `SmartAppFindUsagesProvider` зарегистрирован в `plugin.xml` для
языка JSON и чужой `FakePsiElement` обслуживать не начнёт. Поэтому вводится
собственная фабрика `SmartAppFindUsagesHandlerFactory` (EP
`com.intellij.findUsagesHandlerFactory`), и в ней перечислены **все** случаи:

| Элемент под кареткой | Что делает фабрика | Результат |
|---|---|---|
| `SmartAppRegistrationElement` (наш fake-элемент, цель ссылки) | отдаёт handler, чей `processElementUsages` обходит JSON-файлы приложения по PSI | использования в JSON |
| `JsonStringLiteral` со ссылкой на кастомное слово (Alt+F7 прямо на значении `type`) | резолвит ссылку и делегирует тому же handler'у | те же использования, без перехода в Python |
| Элемент Python PSI (есть `python-ce`), чей диапазон покрыт регистрацией из индекса | тот же handler | использования в JSON |
| `.py` без Python-плагина (plain text) | не берётся: под кареткой файл целиком, различить регистрацию нечем | направление недоступно, пишем в README |

Переход (Go to Definition) отдельно от usages: `SmartAppCustomKeywordReference`
на `JsonStringLiteral` резолвится в `SmartAppRegistrationElement`
(`FakePsiElement` + `PsiNamedElement`), навигация — `OpenFileDescriptor(файл,
offset)`.

**Откуда берутся вхождения.** Обратного индекса использований в плагине нет —
`SmartAppDefinitionIndex` хранит только определения, а `ReferencesSearch` по
`FakePsiElement` полагаться нельзя. Заводить ради этого пятый `FileBasedIndex`
не будем: handler обходит JSON-файлы приложения по PSI
(`FileTypeIndex.getFiles(JsonFileType, applicationScope)`), проверяя значение
`type` тем же `SmartAppTypeContext`, что и подсветка. Так у нас один источник
правды о позициях и никакой версии индекса; Find Usages — явное действие
пользователя с прогрессом, а объём ограничен приложением. Если обход окажется
медленным на больших наборах, правильный ответ — индекс использований
`(категория, имя) -> вхождения`, и это записано в бэклог, а не сделано впрок.

Границы обхода:

- **битый JSON**: вхождения ищутся по частичному PSI, как и всё остальное, —
  строгость применяется только к вкладу файла в индекс определений;
- **дубли**: каждое вхождение — отдельное использование, схлопывание не делаем;
- **вложенные приложения**: scope рекурсивен и захватывает `subapp`, поэтому
  каждый файл-кандидат проверяется правилом владения из раздела 2
  (`applicationRoot(файла) == applicationRoot(регистрации)`). Scope отвечает за
  скорость, фильтр — за корректность; кейс с одинаковым словом во внешнем и
  вложенном приложении обязателен.

`includeDeclaration`: объявление — строка регистрации; при `false` она из
списка исключается.

**Rename не поддерживается** конструктивно: элемент не реализует `setName`, а
`handleElementRename` ссылки возвращает элемент без правки (как у `main_form`).

**Гейт и его границы.** Автоматически проверяются два случая, и оба работают на
`intellijIdeaCommunity` из maven, то есть в CI:

- `myFixture.findUsages` на значении `type` в JSON — сценарий Alt+F7 целиком;
- фабрика, вызванная с `SmartAppRegistrationElement` напрямую, отдаёт handler и
  находит JSON-вхождения.

Случай «каретка в Python-файле» автоматическим гейтом **не покрывается**: в
тестовой платформе нет `python-ce`, а без него `.py` — plain text, и элемента
уже нужного вида не существует. Тянуть Python-плагин в тестовую платформу ради
одной ветки не будем. Значит: сценарий проверяется вручную в GIGA IDE при
приёмке и записывается в README как поведение, зависящее от наличия
Python-плагина. Если ручная проверка провалится — направление «из Python»
уходит в бэклог, JSON-сторона от этого не страдает.

## 5. Грамматика сканера

Сканер — детерминированный line-oriented разбор с отслеживанием отступов, порт
1:1 в обе реализации. Ему нужны три вещи: пропуск строк и комментариев, знание
границ `class`/`def`, распознавание присваивания в реестр.

**Принимается:**

| Форма | Пример |
|---|---|
| подписка по имени | `actions["custom_action"] = CustomAction` |
| подписка по атрибуту | `ffd.field_filler_description["custom_filler"] = C` |
| длинный путь модуля | `core.basic_models.actions.basic_actions.actions["x"] = C` |
| `update` со словарным литералом | `actions.update({"x": C, 'y': D})` |
| кавычки | `"x"`, `'x'`, `"""x"""`, `'''x'''` |
| escape в имени | `"x\u0041"` — имя декодируется по правилам Python-литерала |
| перенос строки внутри скобок | `actions.update({\n  "x": C,\n})` |

**Отвергается (молча, без диагностики):**

| Форма | Почему |
|---|---|
| `actions[name] = C`, `actions[NAME_CONST] = C` | ключ не константа |
| `actions[f"{p}_x"] = C` | f-строка |
| `actions["a" + "b"] = C` | конкатенация |
| `actions.update(mapping)`, `actions.update(**kw)` | аргумент не литерал |
| `for k, v in …: actions[k] = v` | динамика |
| `setdefault`, `dict(...)`, распаковка | не покрыто контрактом |
| присваивание вне `class` → `def init_*` | контракт: `methodPrefix` |
| регистрация во вложенном `class`/`def` внутри `init_*` | неоднозначно, не встречается |
| `RESOURCES` присвоен внутри `if`/`try`/`with`/`def`/`class` | ветку выбрать нельзя, приложение считается динамическим (раздел 1) |
| `RESOURCES = get_resources()` | вычисляемое значение |

**Результат сканера — фиксированная запись.** Без неё «порт 1:1» проверить
нельзя: две реализации могут вернуть одно и то же имя в разных координатах.

```
CustomKeyword {
  category   // категория из таблицы контракта (по имени реестра)
  name       // ДЕКОДИРОВАННОЕ значение литерала: "custom\u0041" -> "customA"
  nameStart  // СЫРОЕ смещение начала содержимого литерала (после кавычки)
  nameEnd    // сырое смещение конца содержимого (перед кавычкой)
  className  // текст правой части, если это идентификатор ("CustomAction",
             // "module.CustomAction"); иначе отсутствует — только для подписи
  file       // файл регистрации
}
```

Почему так:

- **имя декодируется**, потому что сравнивается со значением JSON-литерала,
  которое мы тоже декодируем (`JsonStringLiteralDecoder`). Сравнение сырых
  текстов сломалось бы на первом же escape с любой из сторон;
- **диапазон сырой и без кавычек** — тем же правилом живут все наши ссылки
  («использование покрывает имя без кавычек»), и он же служит диапазоном
  вхождения в Find Usages;
- **каретка при переходе** ставится в `nameStart`;
- **многострочный литерал** (`"""x"""`) допустим: диапазон покрывает
  содержимое, каретка — в его начале. Имя с переводом строки внутри не
  запрещаем: в JSON такое значение записать можно, и решать за пользователя
  тут нечего.

Закрепляется тестами с escape-последовательностью и с многострочным литералом —
с обеих сторон, на одной таблице входов.

**Что сканер обязан игнорировать:** содержимое строк и docstring'ов (в
`custom_app_resources.py` docstring содержит слово `RESOURCES` — попасться на
нём нельзя), комментарии `#`, продолжения строк.

Одинаковость двух реализаций фиксируется одной таблицей входов в юнит-тестах с
обеих сторон (как `isOfferablePath`) плюс кейсами корпуса на реальном файле.

## 6. Конфликты, наследование и MRO

Объединять регистрации цепочки нельзя: Python выполняет `init_*` производного
класса, и базовые регистрации попадают в словарь, **только** если производный
метод вызвал `super()`. Правила разрешения:

| Случай | Решение |
|---|---|
| Производный класс переопределяет `init_X` и вызывает `super().init_X()` | Регистрации базы учитываются, затем поверх — свои; при совпадении `(категория, имя)` эффективна **регистрация производного класса**, она же цель перехода |
| Производный `init_X` **не** вызывает `super()` | Регистрации базы для этой категории не учитываются вовсе — их не будет и в рантайме |
| Две регистрации одного `(категория, имя)` внутри одного метода | Побеждает последняя по документу — семантика Python |
| Одно имя в разных реестрах (`actions["x"]` и `requirements["x"]`) | Независимы: ключ индекса — пара `(категория, имя)`, переход из позиции ведёт в регистрацию её категории |
| Любая множественная база (`class C(A, B)`) | Цепочка не сканируется вовсе: кастомных слов нет — ни при двух базах приложения, ни при комбинации «база приложения + библиотечный миксин». `super()` идёт по MRO, а не по обходу видимых файлов: библиотечный миксин может определять свой `init_actions`, влиять на результат и оставаться для сканера невидимым. Доказать обратное можно, только разрешая MRO вместе с библиотечными модулями, — это v2 |
| Ключевые аргументы в заголовке класса (`class C(Base, metaclass=M)`) | Базой не считаются: учитываются только позиционные аргументы. `class C(Base, metaclass=M)` — одна база, сканируется |

Итог: на пару `(категория, имя)` приходится **ровно одна эффективная
регистрация** — самая производная. Ссылка остаётся поли-вариантной (это дёшево
и страхует от неожиданной раскладки), но в норме отдаёт одну цель.

**Конфликт с фреймворковым словом.** Приложение может зарегистрировать имя,
которое уже есть в снимке фреймворка:

| Случай | Решение |
|---|---|
| Имя совпадает с фреймворковым | Слово остаётся ключевым (объединение множеств). Переход ведёт в регистрацию приложения — во фреймворк прыгать некуда, его исходников в проекте нет. Find Usages показывает вхождения в JSON приложения и саму регистрацию |
| Две регистрации приложения с одним `(категория, имя)` | Резолвер уже сворачивает их в одну действующую (самую производную) — цель перехода одна, это закреплено тестами цепочки |
| Одно имя в разных категориях | Независимы: ключ — пара `(категория, имя)`, переход из позиции ведёт в регистрацию её категории |
| Категория позиции не определена | Ссылка поли-вариантная: целями становятся все регистрации приложения с таким именем — ровно как подсветка в этом случае откатывается к «любой категории» |

**Фреймворковые слова не вычитаются.** Если производный `init_actions` не
вызвал `super()`, строго говоря, фреймворковых действий в рантайме не будет —
но из словаря `keywords.json` мы их не убираем: снимок фреймворка это
единственный источник этих имён, а погасить подсветку целой категории из-за
текстовой эвристики про `super()` — цена несопоставимо выше пользы. Осознанное
отступление от рантайм-семантики: словарь фреймворка играет роль пола,
приложение только добавляет.

`super()` распознаётся текстово (`super().init_X(`, `super(<...>).init_X(`) —
это ограничение записано в рисках.

## 7. Жизненный цикл индекса

**Единица пересборки — приложение, а не файл.** Правка базового ресурса,
переименование модуля, изменение импорта в цепочке — всё это меняет словарь
активного класса, хотя изменившийся файл сам по себе может не содержать ни
одной регистрации. Поэтому изменение любого подходящего `.py` внутри корня
приложения (и `app_config.py` в том числе) запускает **атомарный пересбор
цепочки этого приложения**: резолв от `RESOURCES`, обход баз, замена набора
слов приложения целиком. Частичное обновление одного файла было бы неверным.

VS Code:

- **корни приложений** пересчитываются из уже существующих событий по
  `static/references`; новый корень запускает первичное сканирование своих `.py`;
- **корень исчезает**, когда из него ушёл последний DSL-файл: слова этого
  приложения снимаются, а сам корень забывается — вернувшийся набор обязан
  вызвать полное пересканирование, за время отсутствия Python мог смениться
  (реализовано и закреплено тестом в этапе 2);
- **watcher** — один на воркспейс (`**/*.py`); фильтрация «внутри известного
  корня, владелец — этот корень, каталог не исключён» делается в обработчике.
  Отдельные watcher'ы на корень пришлось бы пересоздавать при каждом изменении
  набора корней;
- **несохранённые файлы**: `onDidOpenTextDocument` и `onDidChangeTextDocument`
  для `.py` работают так же, как для JSON, — с тем же дебаунсом и тем же
  счётчиком поколений. Новый, ещё не сохранённый Python-файл участвует в
  словаре; при закрытии без сохранения приложение пересобирается по содержимому
  с диска;
- **готовность**: `isReady()` истинно только после обоих первичных сканирований
  — JSON и Python. Иначе кастомные слова первые секунды выглядели бы
  неизвестными, а потом «вдруг» становились ключевыми;
- **исключения путей** (`venv`, `.venv`, `site-packages`, `__pycache__`,
  `node_modules`, `build`, `dist`) приходят из контракта и применяются и в
  `findFiles`, и в обработчике watcher'а.

IDEA: `FileBasedIndex` хранит **регистрации по файлам** и ничего не знает о
цепочке — индексатор видит один файл и обязан быть от него независим. Цепочка
разрешается на запросе и кэшируется `CachedValuesManager` с зависимостью от
`PsiModificationTracker.MODIFICATION_COUNT`: правка любого Python-файла
инвалидирует кэш, и цепочка пересобирается — тот же «атомарный пересбор», но
руками платформы. Dumb-guard нужен, потому что чтение индекса в dumb mode
запрещено; фреймворковые слова продолжают работать всегда.

## 8. Порядок генерации контракта и словаря

Таблица «реестр → категория» переезжает из `tools/generate_keywords.py` в
`SmartAppContract` и попадает в `rules.json`; генератор читает её оттуда и
своей копии не держит. Отсюда жёсткий порядок при изменении таблицы:

```bash
./gradlew :idea-plugin:exportRules        # 1. Kotlin-таблицы → shared/rules/rules.json
python tools/generate_keywords.py         # 2. читает таблицу из rules.json → keywords.json
./gradlew :idea-plugin:exportRules --check && python tools/generate_keywords.py --check
npm --prefix vscode-extension run verify:contract
```

Генератор падает с внятным сообщением, если секции в `rules.json` нет или она
пуста — тихо сгенерировать словарь по пустой таблице он не должен. Порядок
попадает в `AGENTS.md` (таблица команд) — в CI джобы независимы, потому что
проверяют уже закоммиченные снимки, а вот локально порядок неочевиден.

## Контракт (версия 5)

```jsonc
"keywordRegistries": { "actions": "action", "requirements": "requirement", … },
"resourceScan": {
  "configFile": "app_config.py",
  "resourcesVariable": "RESOURCES",
  "methodPrefix": "init_",
  "fileExtension": ".py",
  "packageInitFile": "__init__.py",
  "maxBaseDepth": 8,
  "excludedDirs": ["venv", ".venv", "site-packages", "__pycache__", "node_modules", "build", "dist"]
}
```

`contractVersion` 4 → 5 (новая обязательная секция), синхронно правятся
`rules.schema.json` и `EXPECTED_CONTRACT_VERSION`.

Граница «контракт vs код» соблюдена: имена фреймворка и раскладки — данные,
разбор Python — алгоритм.

## Границы v1

| Поддерживаем | Не поддерживаем |
|---|---|
| Подсветку, автодополнение, переход к регистрации, Find Usages | переименование ключевого слова (правка Python + всех JSON) |

| Цепочку классов от `RESOURCES` внутри приложения — строго одиночное наследование | любое множественное наследование, включая библиотечные миксины (нужен C3 вместе с библиотеками — в бэклог); ресурсы, собранные динамически; классы вне приложения |
| Переход на строку регистрации | переход сразу на класс (`CustomAction`) — требует Python-семантики, ломает паритет; v2 |

## Реестры без контекста позиции

`operators`, `comparators`, `answer_items` есть в таблице реестров (их наполняет
и сам фреймворк), но `TypeContextSpec` ни по структурному ключу, ни по виду
файла такие категории не выдаёт. Замер на ядре расширения: слово
`custom_operator`, зарегистрированное приложением, **не подсвечивается и не
предлагается** — в позиции `requirement.operator.type` категория определяется
как другая, и сравнение по категории отсекает вариант.

Решение для v1: эти три категории из наблюдаемого объёма исключены. Сканер их
собирает (вреда нет, и словарь остаётся полным), но обещать по ним подсветку,
автодополнение и переход мы не можем, пока `typeContext` не научится их
позициям. Это отдельная задача — она про контекст `type`, а не про ресурсы
приложения, и уходит в `docs/plans/backlog.md`.

## Корпус и тесты

Фикстура `custom-app-resources/` — два приложения:

```
app_a/app_config.py                              RESOURCES = CustomAppResources
app_a/app/resources/base_resources.py            actions["base_action"], actions["shared"] = BaseAction
app_a/app/resources/custom_app_resources.py      class CustomAppResources(BaseResources):
                                                   init_actions  -> super() + actions["custom_action"],
                                                                    actions["shared"] = CustomAction
                                                   init_requirements -> без super(), свои слова
app_a/app/resources/unused_resources.py          наследник, на который RESOURCES не указывает
app_a/static/references/actions/actions.json     "type": "custom_action"
app_a/subapp/app_config.py + static/references/… вложенное приложение со своим словом
app_b/app_config.py + static/references/…        соседнее приложение, чужих слов не видит
```

Что этой раскладкой проверяется: `super()` (в `app_a` есть и `base_action`, и
`custom_action`), переопределение (`shared` ведёт в производный класс, не в
базовый), отсутствие `super()` (слова базы для requirement'ов не появляются),
неиспользуемый наследник, вложенное и соседнее приложения.

### Что корпус проверить может, а что нет

Каретка в корпусе — это JSON-позиция: README описывает `anchor` как подстроку
DSL-файла, IDEA-раннер требует под кареткой `JsonProperty`/`JsonStringLiteral`,
а Python-файл в плагине — plain text. Значит направление «каретка в Python →
использования» корпусом не выражается вовсе, и притворяться, что выражается, не
будем. Оно и так платформенное: без `python-ce` элемента нужного вида нет
(раздел 4).

Поэтому корпус фиксирует три вещи, и все они выражаются в текущем формате:

| Секция | Что проверяет | Что нужно от раннеров |
|---|---|---|
| `customKeywords` (новая) | сам словарь приложения: `category`, `name`, файл регистрации, строка и `rangeText` | обе стороны отдают его из своего резолвера — ни PSI, ни каретка не нужны |
| `definitions` | переход с `"type"` в JSON на строку регистрации в `.py` | цель — файл вне DSL, как у шаблонов: `file` + `line` + `rangeText`; уже поддержано |
| `references` | Alt+F7 на значении `type` в JSON: вхождения в JSON приложения плюс сама регистрация | источник — JSON-позиция, то есть текущий формат; фильтр вложенных приложений проверяется здесь же |

Плюс прежние секции: `semanticTokens` (кастомное слово подсвечено как ключевое)
и `completion` (`kind: "keyword"`, `custom_action` есть в app_a и **отсутствует**
в app_b и среди слов из `unused_resources.py`).

Добавление секции `customKeywords` — работа по обеим сторонам сразу: раннер,
который её не знает, обязан падать (`SUPPORTED_SECTIONS`), иначе она станет
молчаливо непроверенным контрактом.

Отдельно, вне корпуса: таблица форм сканера с обеих сторон (все строки раздела
5, включая отвергаемые); dumb mode в IDEA; исключение `venv`; резолв цепочки баз;
`app_config.py` без `RESOURCES`; `RESOURCES` в ветке `if` (слов нет);
**вложенные приложения** (`project` и `project/subapp` — слово внутреннего не
видно снаружи и наоборот); наследование — три кейса: `super()` + переопределение
(цель — производная регистрация), отсутствие `super()` (базовые слова не
учитываются), правка базового файла пересобирает словарь производного;
**IDEA-тесты Find Usages** — Alt+F7 на значении `type` в JSON и фабрика с
`SmartAppRegistrationElement` напрямую (раздел 4); **множественная база** — два негативных
кейса: `class C(AppBaseA, AppBaseB)` и `class C(AppBase, LibraryMixin)`, в обоих
слов нет; **контракт результата** — escape (`"custom\u0041"` →
имя `customA`, диапазон на сыром тексте) и многострочный литерал.

Раннерам корпуса потребуется принимать `.py` как файл фикстуры: в Kotlin
`addFileToProject` справится, в TS `upsert` уже умеет. Каретку в `.py` ставить
не потребуется — см. таблицу выше.

## Проверка

```bash
export JAVA_HOME="/Applications/GIGA IDE CE 2025.1.app/Contents/jbr/Contents/Home"
./gradlew :idea-plugin:exportRules --check :idea-plugin:test
npm --prefix vscode-extension test && npm --prefix vscode-extension run test:integration
python tools/generate_keywords.py --check
```

Мутации: указать `RESOURCES` на неиспользуемый класс → падает кейс с
`unused_resources.py`; заменить правило владения на «любой предок» → падает кейс
вложенных приложений; объединять регистрации цепочки вместо разрешения по
`super()` → падает кейс наследования; обновлять только изменившийся файл вместо
пересбора приложения → падает кейс правки базового класса; убрать пропуск
docstring → сканер найдёт слово в тексте документации и уронит негативный кейс;
разрешить сканирование при одной базе приложения и библиотечном
миксине → падает негативный кейс `class C(AppBase, LibraryMixin)`; снять исключение `venv` в `InputFilter` или в резолвере импортов →
падает парный тест `venv`; отдавать сырое имя вместо декодированного → падает
тест escape;
забыть dumb-guard → падает тест индексации; разойтись сканерам на одной форме →
падает общая таблица.

Ручная приёмка на эталонном проекте (GIGA IDE, где есть `python-ce`):
`custom_action` подсвечен, предлагается в `actions.json`, ведёт в
`custom_app_resources.py:32`, Alt+F7 на значении `type` показывает
`actions.json:27`. Отдельно — единственный сценарий вне автоматического гейта:
Alt+F7 **на самой регистрации** в Python-файле.

## Риски

1. **Стоимость первичного сканирования** Python в больших монорепо: ограничена
   корнями приложений и списком исключений, но гарантий по размеру нет — та же
   политика best-effort, что у каталога шаблонов.
2. **Резолв импортов** — текстовый: относительные импорты (`from .x import Y`),
   `importlib`, условные импорты не поддерживаются. Для эталонной раскладки
   этого достаточно, для экзотической — слов не будет, молча.
3. **Направление «Python → JSON» в IDEA** зависит от наличия Python-плагина.
   В GIGA IDE CE он есть (`python-ce`), в чистой IDEA CE — нет.
4. **Расхождение сканеров** — главный риск паритета; закрывается общей таблицей
   форм и кейсами корпуса, иначе не ловится ничем.
5. **`super()` распознаётся текстово.** Вызов через переменную, `getattr` или
   вспомогательный метод не будет замечен, и базовые слова окажутся
   неучтёнными. Направление ошибки выбрано осознанно: пропустить слово хуже
   лишнего только тем, что оно не подсветится, — ложная подсветка того, чего в
   рантайме нет, вводила бы в заблуждение сильнее.
6. **Схема Find Usages в IDEA — под гейтом теста** (раздел 4), но сценарий
   «каретка в Python-файле» автоматическим гейтом не покрывается: в тестовой
   платформе нет `python-ce`. Проверяется вручную, риск остаётся.
7. **Любое множественное наследование ресурсов** гасит фичу целиком для такого
   приложения — включая безобидный на вид `class C(AppBase, LoggingMixin)`.
   Выбор осознанный: библиотечная база невидима сканеру, но участвует в MRO, и
   догадка о порядке показывала бы слова, которых в рантайме нет. Если такая
   раскладка встретится в бою, правильный ответ — не ослабить правило, а
   научиться читать библиотечные модули (v2).
