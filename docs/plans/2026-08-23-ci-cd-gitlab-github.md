# CI/CD в GitLab и GitHub: общая логика в `tools/ci`, тонкие конфиги

## Контекст

`.gitlab-ci.yml` написан вместе с монорепозиторием и **лежит на remote'е**:
`origin/feature/monorepo-idea-and-vscode` (8bc4b20, 2026-08-20) содержит его,
`origin/master` — нет. Локальный `HEAD` опережает эту точку на 38 коммитов.

Запускался ли пайплайн — из репозитория не видно: анонимный GET к
`https://gitlab.com/api/v4/projects/lyobzik%2Fnlpf-idea` отвечает 404, проект
приватный. Поэтому первым идёт не конфиг, а взгляд на уже случившееся (этап 0).

Задача: довести CI до состояния, подтверждённого прогоном, добавить CD (релиз по
тегу) и запускать те же проверки на двух хостингах — GitLab (основной) и GitHub
(зеркало).

### Что измерено локально

| Факт | Значение | Откуда |
|---|---|---|
| Дистрибутив платформы из maven | ~1.2 ГБ на версию (в кэше 3.2 ГБ на три) | `~/.gradle/caches/modules-2/files-2.1/idea/ideaIC` |
| Кэш верификатора плагина | 3.6 ГБ, всё в `loaded-plugins`; `ides/` пуст | `~/.pluginVerifier` |
| `verifyPlugin` **по умолчанию** | пять IDE: IC-251, IC-252, IU-253, IU-261, IU-262 | прогон на реализации |
| `verifyPlugin` с явным списком | две IDE; проверка 4 м 58 с, весь прогон 13 м 31 с с загрузкой IU-262 | прогон на реализации |
| Кэш VS Code для интеграционных тестов | 1.4 ГБ | `vscode-extension/.vscode-test` |
| Лимит бесплатного тарифа gitlab.com | 400 compute-минут в месяц | тариф GitLab |
| Проект на gitlab.com | приватный (API 404 без токена) | `curl` к API |

Главная статья расходов — платформа IntelliJ. `exportRules` зависит от
`sourceSets.main.output`, поэтому её тянет **и** проверка снимка контракта;
комментарий в [build.gradle.kts:44](../../idea-plugin/build.gradle.kts:44)
описывает runtime-classpath экспортёра и про job вводит в заблуждение.

## Решения

Принятые оператором:

1. **Runner'ы** — только shared на gitlab.com.
2. **Запуск** — MR + `master` + релизные теги + ручной; ветка без MR пайплайн не
   создаёт.
3. **CD** — релиз только по защищённому тегу `v<версия>`: артефакты в Generic
   Package Registry, GitLab Release со ссылками. Marketplace/OpenVSX — в бэклоге.
4. **Два хостинга**, общая логика в `tools/ci/`; полный пайплайн — GitLab,
   GitHub остаётся лёгким.
5. **Владелец релиза один — GitLab.** GitHub на теге только проверяет.
6. **`verifyPlugin` обязателен** на каждом MR, `master` и релизном теге.
7. **Сторона IDEA на GitHub не запускается**, включая `contract:rules`;
   выделение модуля `:contract` — отдельная задача.

Принятые в этом плане (закрывают семь замечаний ревью):

8. **Стадия `contract` проверяет не весь контракт данных.** Kotlin-снимок
   проверяется первой задачей внутри `test:idea` — см. «Что блокирует что».
9. **На релизном теге сторона IDEA собирается в том же job'е**, что тестируется:
   отдельный `package:idea` на теге не появляется.
10. **Публикация сериализуется `resource_group` и не прерывается**
    (`interruptible: false`), а гонка на записи обрабатывается явно.
11. **Установка системных пакетов — отдельный скрипт окружения**, а не команды в
    YAML.
12. **Скрипт публикации — на Python**, а не shell+curl+jq, и покрыт локальными
    тестами на фейковом транспорте.
13. **Запрет дублей в реестре недоступен**: проект живёт в личном namespace
    (`lyobzik` — пользователь, `/groups/lyobzik` отвечает 404), а настройка
    групповая. Единственная гарантия — сам скрипт; см. этап 4.
14. **Интеграционный тест VS Code гоняется только в GitLab**, и `deps-debian.sh`
    вызывается только оттуда — детерминированность важнее второй копии смоука.
15. **Перед первым релизом — ручной `release:smoke`** против настоящего API:
    фейковый транспорт проверяет алгоритм, но не GitLab.
16. **Список IDE для `verifyPlugin` задан явно** (`pluginVerification.ides` в
    `idea-plugin/build.gradle.kts`). Выяснилось на реализации: по умолчанию
    плагин платформы берёт `recommended()` — это **пять** дистрибутивов IDE на
    каждый прогон, и набор молча растёт с каждым релизом JetBrains. Проверяются
    два края обещанного диапазона: `platformVersion` (нижний, он же
    `sinceBuild`) и `verifierLatestVersion` (верхний — `untilBuild` не задан,
    значит верх обязан проверяться, а не подразумеваться). API оказался
    `ides { create(type, version) }`, а не `ide(...)`, а Community для верхней
    версии не публикуется — верхний край проверяется на Ultimate.

## Архитектура: четыре роли, у каждой свой критерий

| Файл | Что в нём | Критерий принадлежности | Кто вызывает |
|---|---|---|---|
| `tools/ci/run.sh <шаг>…` | сборка, проверки, упаковка | воспроизводится локально на любой машине | оба хостинга |
| `tools/ci/deps-debian.sh` | `apt-get` для интеграционного теста | зависит от **образа** | только `.gitlab-ci.yml` |
| `tools/ci/publish_gitlab.py` | реестр пакетов и Release | зависит от **API хостинга** | только `.gitlab-ci.yml` |
| `.gitlab-ci.yml`, `.github/workflows/ci.yml` | когда запускать, образ, кэш, отчёты, артефакты | свойство хостинга | — |

Правило остаётся жёстким: **в YAML нет ни одной команды** — только вызовы этих
трёх файлов. Уточняется, что «общая логика» не значит «один файл»: у трёх ролей
разные причины существовать, и смешивать их — значит тащить `apt-get` на macOS
и API GitLab в GitHub.

Инвариант проверяемый: **в `run.sh` нет ни одной переменной хостинга**. Тег
передаётся аргументом (`run.sh contract:version "$CI_COMMIT_TAG"` у GitLab,
`"$TAG"` у GitHub), поэтому `grep -c 'CI_[A-Z]\|GITHUB_' tools/ci/run.sh`
обязан давать 0. В `run.sh` нет также кэшей, артефактов и условий «на какой
ветке»: скрипт, знающий про `CI_COMMIT_BRANCH`, — это третья реализация CI.

## Что блокирует что (замечание 1)

Прежняя формулировка «стадия `contract` блокирует `test`» после переноса
`exportRules --check` внутрь Gradle-job'а стала неверной. Из трёх выходов —
оставить отдельный job и платить второй загрузкой платформы, сделать `:contract`
сейчас, либо честно описать границу — выбран третий: `:contract` отложен
решением 7, а вторая загрузка платформы на каждом MR стоит дороже, чем то, что
она даёт.

Фактическая картина, которую и надо записать в README:

- **Стадия `contract`** проверяет словарь (`keywords.json`), версию манифестов и
  схемы — то есть Python- и TS-часть контракта данных. Она дешёвая (ни одного
  job'а с платформой) и блокирует стадию `test`.
- **Kotlin-снимок `rules.json`** проверяется первой задачей в `test:idea`.
  Устаревший снимок валит пайплайн, но не раньше, чем стартуют VS Code-job'ы:
  впустую тратится их время, а не корректность гейта.
- Когда появится модуль `:contract`, проверка снимка вернётся в стадию
  `contract` и это ограничение исчезнет.

Цена ошибки здесь — минуты на редком сценарии (забыли перегенерировать снимок),
и она ловится локально одной командой до push'а.

## Этап 1 — `tools/ci/run.sh`

```text
tools/ci/run.sh <шаг> [<шаг>…]

contract:keywords     python3 tools/generate_keywords.py --check
contract:version      sh tools/check-version.sh "$1"
contract:schema       npm ci && npm run verify:contract
test:publish          python3 -m unittest discover -s tools/ci -p test_publish_gitlab.py
test:idea             ./gradlew $GRADLE_ARGS -Djava.awt.headless=true \
                        :idea-plugin:exportRules --check \
                        :idea-plugin:test :idea-plugin:verifyPlugin
test:vscode           npm ci && npm run lint && npm run typecheck && vitest (+ junit)
test:vscode:int       npm ci && xvfb-run npm run test:integration
package:idea          ./gradlew $GRADLE_ARGS :idea-plugin:packagePlugin
package:vscode        npm ci && npm run package
```

Шагов можно передать несколько: `run.sh test:idea package:idea` выполняет их
подряд **в одном job'е**, то есть с одной загрузкой платформы. Это и есть ответ
на замечание 2 (см. матрицу ниже).

Что скрипт централизует:

- **`GRADLE_ARGS`** по умолчанию `-PideSource=maven` (локальной IDE нет ни у
  одного хостинга), переопределяется окружением — тот же шаг гоняется локально
  против GIGA IDE. Подстановка `${GRADLE_ARGS-…}`, а не `${GRADLE_ARGS:-…}`:
  `GRADLE_ARGS=` (задано и пусто) обязано означать «никаких флагов, бери
  умолчание из `gradle.properties`», иначе обещание README не выполняется.
- **Лишние аргументы — ошибка, а не мусор.** Каждый шаг объявляет, сколько
  аргументов принимает (`contract:version` — один, остальные — ноль), и лишний
  роняет запуск с кодом 2 **до того, как выполнится первый шаг**. Считаются
  токены, а не непустые строки: пустой тег — валидный аргумент, поэтому
  накапливать аргументы в одну строку нельзя (в ней пустые исчезают, и
  `contract:version "" extra` выглядел бы как один аргумент). В CI лишний токен обычно означает опечатку в имени
  шага, и молчаливое игнорирование превратило бы её в зелёную проверку,
  проверившую не то.
- **JUnit-отчёты в одинаковых путях**: `idea-plugin/build/test-results/test/` и
  новый `vscode-extension/build/test-results/vitest.xml`
  (`--reporter=default --reporter=junit --outputFile.junit=…`). Флаги живут
  здесь, а не в `package.json`: `npm run test:unit` остаётся человеческой
  командой.
- **`xvfb-run` только когда он есть и нет `DISPLAY`** — шаг работает и на macOS,
  и на Linux-runner'е.
- **`npm ci` внутри шага**, а не в `before_script`: у GitHub его нет.

Добавляется `npm run lint`: eslint держит контрактное правило «в `src/core` нет
DSL-литералов и импорта `shared/`» — это проверка контракта, не косметика.

**Fail-fast и обязательность `verifyPlugin` (замечание 6).** Задачи в
`test:idea` идут по возрастанию цены: `exportRules --check` → `test` →
`verifyPlugin`, и при падении ранней поздняя не выполняется. Это оставлено как
есть, потому что защиту оно не ослабляет: слить MR можно только на зелёном
пайплайне, а зелёный означает, что верификатор отработал и прошёл. Формулировка
в документации — «`verifyPlugin` выполняется на каждом успешном пайплайне», а не
«запускается всегда»; разница честная и её надо писать явно.

Правится [tools/package.sh](../../tools/package.sh): Gradle-вызов получает
`${GRADLE_ARGS:-}`, иначе на Linux скрипт уходит в `ideSource=local` и падает на
пути к GIGA IDE.

## Этап 2 — `.gitlab-ci.yml`

Стадии `contract → test → package → release`.

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS && $CI_PIPELINE_SOURCE == "push"'
      when: never
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    - if: '$CI_PIPELINE_SOURCE == "web"'
```

Нерелизный тег (`sandbox`) пайплайна **не создаёт вовсе**: обещать по нему
нечего, а ветка, на которую он поставлен, уже проверена. Ветка без MR тоже не
проверяется — обратная связь до MR берётся локальным `run.sh`.

### Матрица запуска (замечание 5)

| Job | Образ | Шаги `run.sh` | MR | `master` | тег `v*` | ручной (`web`) |
|---|---|---|---|---|---|---|
| `contract:keywords` | `python:3.12-slim` | `contract:keywords` | авто | авто | авто | авто |
| `contract:version` | `python:3.12-slim` | `contract:version "$CI_COMMIT_TAG"` | авто | авто | авто | авто |
| `contract:schema` | `node:22-bookworm` | `contract:schema` | авто | авто | авто | авто |
| `contract:publish` | `python:3.12-slim` | `test:publish` | авто | авто | авто | авто |
| `test:idea` | `eclipse-temurin:21-jdk` | `test:idea` | авто | авто | **нет** | авто |
| `test:idea:release` | `eclipse-temurin:21-jdk` | `test:idea package:idea` | нет | нет | **авто** | нет |
| `test:vscode:unit` | `node:22-bookworm` | `test:vscode` | авто | авто | авто | авто |
| `test:vscode:integration` | `node:22-bookworm` | `deps-debian.sh` + `test:vscode:int` | авто | авто | авто | авто |
| `package:idea` | `eclipse-temurin:21-jdk` | `package:idea` | вручную | вручную | нет | вручную |
| `package:vscode` | `node:22-bookworm` | `package:vscode` | вручную | вручную | **авто** | вручную |
| `release` | `python:3.12-slim` | `publish_gitlab.py "$CI_COMMIT_TAG"` | нет | нет | **авто** | нет |
| `release:smoke` | `python:3.12-slim` | `publish_gitlab.py --smoke` | нет | вручную¹ | нет | вручную¹ |

Читается так:

- `test:idea` и `test:idea:release` — один и тот же базовый job (`extends`) с
  взаимоисключающими правилами; отличие только в списке шагов. На теге сборка
  артефакта идёт **в том же job'е**, где уже скачана платформа, поэтому вторая
  загрузка не возникает. Отдельный `package:idea` остаётся только для ручной
  упаковки на ветке — редкое действие, за которое платим осознанно.
- Ни одна зависимость `release` не может оказаться `skipped`: на теге и
  `test:idea:release`, и `package:vscode` автоматические. `release` объявляет
  `needs` на оба и забирает их артефакты.
- Ручные job'ы упаковки не блокируют пайплайн (`allow_failure: true` в смысле
  «не запущен — не считается провалом»).
- ¹ `release:smoke` — ручная проверка публикации против настоящего API
  (этап 4). Его свойства заданы явно, потому что ручной job легко оставляет
  пайплайн в подвешенном состоянии:

  | Свойство | Значение | Почему |
  |---|---|---|
  | стадия | `release` | публикует в тот же реестр |
  | `when` | `manual` | сеть, чужой API, мусор в реестре — не на каждый push |
  | `allow_failure` | `true` | иначе непрожатая кнопка держит пайплайн в `blocked`, а *Pipelines must succeed* не даёт слить MR |
  | гейт | **не гейт** | результат читает человек, который его нажал; красный смоук не красит пайплайн — это диагностика, а не проверка |
  | `resource_group` | `release` | иначе смоук и настоящий релиз (кто-то поставил тег) полезут в реестр одновременно |
  | тег `smoke` | создаёт Release API из `ref` | отдельного push тега нет, в репозитории он появляется сам |

  На теге job'а нет: релизный пайплайн не должен зависеть от кнопки, которую
  могут не нажать.

### Кэш и загрузка платформы (замечание 2)

Кэш Gradle **не включается**. Причины, и ни одна не про удобство:

- платформа — 1.2 ГБ; GitLab жмёт кэш, кладёт в объектное хранилище и
  распаковывает на каждом job'е, что вполне может быть дольше загрузки с CDN;
- статический ключ `gradle` — гонка между одновременными пайплайнами, которую
  «один писатель» не решает;
- ключ не зависел от конфигурации сборки: смена `platformVersion` оставляла
  прежний кэш.

Реальное число загрузок после матрицы: **одна на пайплайн** — и на MR, и на
`master`, и на теге. Две останутся только если человек нажал ручной
`package:idea` на ветке.

Если числа этапа 0 покажут выгоду кэша, он включается сразу правильно:
`cache:key:files` по `gradle.properties` и `idea-plugin/build.gradle.kts`
(GitLab допускает два файла), `policy: pull` у всех, кроме одного писателя.

Мелочи: `retry` на `runner_system_failure` и `stuck_or_timeout_failure`,
`interruptible: true` по умолчанию — и `interruptible: false` у `release`.

## Этап 3 — `.github/workflows/ci.yml` (лёгкий)

```yaml
on:
  pull_request:
  push:
    branches: [master]
    tags: ["v*"]
  workflow_dispatch:
```

Плюс `concurrency` с `cancel-in-progress` и `permissions: contents: read` —
писать этому пайплайну нечего. Actions закрепляются по commit SHA — так же, как
образы GitLab по digest: `@v4` — движущийся тег, и без пина содержимое gate'а
меняется без единой правки в репозитории.

**Фильтр тегов у GitHub намеренно шире (замечания 4 и 5).** Синтаксисы разные —
у GitLab регулярное выражение, у GitHub glob-паттерн, — и попытка выразить один
через другой даёт утверждение, которое здесь нечем проверить: GitHub-репозитория
пока нет. Поэтому равенство фильтров не изображается: GitHub запускается на
любом `v*`, а окончательную фильтрацию делает `contract:version`, который идёт на
обоих хостингах.

Проверено исполнением (regexp GitLab и `tools/check-version.sh` на манифестах
`0.1.0`):

| Тег | GitLab: пайплайн | `contract:version` |
|---|---|---|
| `v0.1.0` | да | зелёный, релиз |
| `v1.10.1` | да | красный (версия манифестов другая) |
| `v1.2` | нет | — |
| `vfoo` | нет | зелёный: тег не похож на версию, релизным не считается |
| `v0.1.0-beta` | нет | красный: похож на версию и не совпадает с ней |

Читается так: лишний прогон на GitHub стоит бесплатных минут и ничего ложного не
обещает — `vfoo` даёт зелёные проверки, не делая релиза, а `v0.1.0-beta`
краснеет там же, где покраснел бы в GitLab. Пред-релизные теги не
поддерживаются: `check-version.sh` требует точного `v<версия>`.

Состав: `contract:keywords`, `contract:version`, `contract:schema`,
`test:publish`, `test:vscode`. Ни одного шага со стороны IDEA, включая
`contract:rules`, — Java на runner'е не нужна вовсе, хватает `setup-node@v4`
(22, кэш npm) и `setup-python@v5` (3.12).

**Интеграционного теста VS Code на GitHub нет (замечание 2).** Прежняя
формулировка «если чего-то не хватит, вызовет тот же скрипт» ничего не решала:
`deps-debian.sh` пишется под Debian-контейнер GitLab, где job идёт от root, а
`ubuntu-latest` — Ubuntu без root (нужен `sudo`) и с другими именами пакетов
(`libasound2` против `libasound2t64`), и workflow не умеет добавлять шаг после
проверки того, чего не хватает. Из трёх выходов — двухдистрибутивный скрипт,
подготовленный образ, отказ — выбран третий: интеграционный смоук проверяет
регистрацию провайдеров в настоящем редакторе, GitLab делает это на каждом
пайплайне, и вторая копия не стоит недетерминированного окружения. Понадобится
она на GitHub — правильный ответ будет «подготовленный образ», а не ветвление
по дистрибутиву.

Тег на GitHub запускает те же проверки и **не создаёт релиза**.

**В README обязательно:** зелёный статус GitHub означает «словарь, версии,
схемы, тесты публикации и юнит-сторона VS Code в порядке». Снимок `rules.json`,
тесты плагина, верификатор и интеграционный тест VS Code там не проверяются.

## Этап 4 — CD: релиз по тегу (только GitLab)

Версия берётся как `${CI_COMMIT_TAG#v}`: совпадение тега с манифестами уже
гарантировал `contract:version`.

Публикацию целиком делает один job `release` (`needs` на `test:idea:release` и
`package:vscode`). Разносить загрузку по job'ам упаковки нельзя: упавший
`release` оставил бы пакеты в реестре без релиза.

**Инструмент — `tools/ci/publish_gitlab.py` на `python:3.12-slim`, пин по
digest.** Ни `release-cli` (устарел), ни ключевое слово `release:`:
идемпотентность требует «прочитать → сравнить → решить», а keyword умеет только
создавать и падает на существующем релизе. Python выбран вместо `curl`+`jq`
потому, что образу тогда не нужно ничего доустанавливать: HTTP (`urllib`),
JSON (`json`), SHA-256 (`hashlib`) — стандартная библиотека, а образ уже
используется другими job'ами.

### Идемпотентность и гонки (замечания 3 и 7)

1. **Запрет дублей в реестре недоступен — и на него нельзя опираться.**
   Настройка живёт на уровне группы (`Group → Settings → Packages and
   registries → Generic packages duplicates`, роль Owner/Maintainer группы, плюс
   regexp-исключения), а проект лежит в **личном** namespace: `lyobzik` —
   пользователь, `GET /groups/lyobzik` отвечает 404, страницы групповых настроек
   у него нет. Значит реестр дубликаты разрешает, и это не настраивается.

   Следствие для алгоритма: файлов с одним именем в версии может оказаться
   несколько. Правило — **все файлы с искомым именем обязаны иметь один и тот же
   `file_sha256`, совпадающий с локальным**; иначе ошибка. Проверять «первый
   попавшийся» нельзя: какой из дублей отдаст ссылка скачивания, реестр не
   обещает.

   Если проект когда-нибудь переедет в группу, `Deny` ставится там же и
   становится вторым рубежом; исключение по имени `smartapp-dsl` при этом не
   должно совпадать ни с одним regexp в списке. Действующий режим показывает
   `release:smoke` — он делает второй **прямой** `PUT` мимо алгоритма (через
   идемпотентную публикацию дубль не создать: она увидит тот же хеш и не станет
   загружать) и смотрит, прошёл тот или отказал. Другого способа узнать режим у
   личного namespace нет: страницы групповых настроек у него не существует.
2. `resource_group: release` — GitLab сериализует job'ы одной группы по всему
   проекту, поэтому двух одновременных публикаций одного тега не бывает.
3. `interruptible: false` — иначе auto-cancel остановит job между загрузкой
   первого пакета и созданием Release.
4. Гонка всё равно обрабатывается явно, потому что `resource_group` защищает от
   параллельности, но не от повторного запуска после отказа сети:
   - **пакет:** `GET /projects/:id/packages` → `package_files`, сверка
     `file_sha256`. Нет файла → `PUT`. Есть, хеш совпал → успех (повтор). Есть,
     хеш не совпал → **ошибка**: тот же тег даёт другой артефакт, значит тег
     переставили или сборка недетерминирована.
   - **Отказ `PUT` разбирается по состоянию, а не по коду ответа.** Запрет
     дублей отвечает `400 Duplicate package is not allowed`, гонка может дать
     `409`, а разбирать текст сообщения — значит зависеть от его формулировки.
     Правило: любой отказ `PUT` → перечитать `package_files` → если состояние
     верное (все файлы с этим именем имеют нужный хеш), шаг успешен; иначе
     ошибка с исходным кодом и телом ответа. Так обрабатываются и `400`, и
     `409`, и то, чего мы ещё не видели, а настоящая ошибка запроса остаётся
     ошибкой, потому что состояние после неё неверное.
   - **Release:** `GET /projects/:id/releases/:tag` → 404 → `POST`. 200 →
     сравнить набор ссылок по спецификации ниже. Конфликт при `POST` →
     повторное чтение и та же сверка.
   - **Пагинация:** `package_files` отдаётся по 20 записей; страницы
     обходятся до конца, иначе второй артефакт «не найдётся» и будет залит
     повторно.

5. **Релиз не выпускается без доказательства, что тег защищён.** Первое, что
   делает job — до единой загрузки в реестр — читает
   `GET /projects/:id/protected_tags`:

   | Ответ API | Решение |
   |---|---|
   | тег покрыт шаблоном | публикуем |
   | тег не покрыт | **отказ** |
   | список недоступен | **отказ** (fail-closed) |

   Третья строка — результат отброшенной попытки схитрить. Сигнала из
   окружения, который годился бы в доказательство, **не существует**: переменные
   вручную запущенного пайплайна перекрывают предопределённые, включая
   `CI_COMMIT_REF_PROTECTED`. Значит либо ответ API, либо отказ.

   Чтобы отказ не стал вечным (`CI_JOB_TOKEN` к `/protected_tags` не
   допускают), у job'а **два транспорта**: job-токен грузит артефакты и создаёт
   релиз, а токен проекта с областью `read_api` — читает настройки. Второй
   задаётся защищённой маскированной переменной `SMARTAPP_API_TOKEN`; нет его —
   релиза нет. Подставить в неё чужое значение бессмысленно: доказательством
   служит ответ API, а не факт наличия переменной.

   Список правил обходится **постранично**: правило `v*` может оказаться и на
   второй странице, и «не нашли» тогда означало бы «не защищён» — отказ на
   ровном месте.

   **Адрес API и проект зафиксированы в коде.** Переопределяемы не только
   `CI_COMMIT_REF_PROTECTED`: подменив `CI_API_V4_URL`, запуск отправил бы оба
   токена на чужой хост, который вернул бы любой удобный ответ про защиту тега;
   подменив `CI_PROJECT_ID`, можно было бы «доказать» защиту на чужом проекте,
   где она включена. Поэтому `API_URL` и `PROJECT_PATH` — константы скрипта.
   Окружение не игнорируется: расхождение `CI_API_V4_URL` или `CI_PROJECT_PATH`
   с ними — отказ, потому что означает либо запуск не там, либо попытку
   подмены. Совпадение требуется **точное**, а пустое или отсутствующее
   значение — такой же отказ, как чужое: иначе guard выключался бы пустой
   pipeline variable. В настоящем job'е обе переменные выставляет GitLab, так
   что их отсутствие само по себе означает запуск не там, где скрипт думает. Операционное следствие: **переезд или переименование проекта
   требует правки константы**, и это правильно — такой переезд обязан быть
   осознанным изменением в репозитории.

   Отдельно про `CI_COMMIT_SHA`: он тоже приходит из окружения и в ручном
   пайплайне переопределяем, поэтому сверка «коммит тега = коммит пайплайна» —
   **вспомогательная**. Основную защиту даёт сверка коммита релиза с коммитом
   тега: оба значения читаются из API.
6. **Созданный релиз проверяется сразу, а не при следующем запуске.** Между
   чтением коммита тега и `POST /releases` тег могут переставить — тогда релиз
   привязан к одному коду, а артефакты собраны из другого. Помешать этому
   скрипт не может: атомарной привязки «создай релиз на коммите X» в API нет.
   **Неизменность обеспечивает protected tag** (этап 5) — именно он, а не
   скрипт, запрещает двигать `v*`; задача скрипта — чтобы нарушение немедленно
   всплыло, поэтому ответ `POST` прогоняется через ту же сверку ссылок и
   коммита, что и существующий релиз. Ответ без `commit` перечитывается через
   `GET`.
7. **Релиз без своего тега — ошибка.** Если релиз есть, а тег удалён, сверить
   его не с чем: `ref` в этом случае не повод считать состояние нормальным.
   Раньше такой случай проходил зелёным в смоуке.
8. **У HTTP-запросов конечный таймаут** (60 с). Зависший API иначе держит
   релизный job до общего таймаута runner'а вместо внятного отказа, после
   которого job просто перезапускают — публикация идемпотентна, повтор
   безопасен.

Итог: повторный запуск `release` после любого частичного отказа доводит
публикацию до конца либо падает с внятной причиной, но не создаёт второго
состояния.

### Спецификация ссылок Release (замечание 6)

Без этого две реализации сочтут один и тот же релиз то корректным, то
повреждённым. Ссылок ровно две, по одной на артефакт:

| Поле | Значение |
|---|---|
| `name` | имя файла: `smartapp-dsl-<версия>.zip` и `smartapp-dsl-<версия>.vsix` — человек в UI видит ровно то, что скачает |
| `url` | `<API_URL>/projects/<PROJECT_PATH>/packages/generic/smartapp-dsl/<версия>/<имя>`, где обе части — константы скрипта, а путь проекта закодирован (`lyobzik%2Fnlpf-idea`) |
| `link_type` | `package` |
| `direct_asset_path` | **не задаётся**: второй адрес той же вещи — второй повод разъехаться |

Сравнение при существующем релизе: множества троек `(name, url, link_type)`
обязаны совпасть **точно**. Недостающая ссылка — ошибка (публикация не
доведена). Лишняя — тоже ошибка: релиз описывается сборкой, и если кто-то
приложил артефакт руками, это должен увидеть человек. Удалять чужое скрипт не
станет ни при каком раскладе.

**Сверяется и commit — но с коммитом тега, а не с коммитом пайплайна.**
Перемещённый тег иначе проходит незамеченным: артефакты, хеши и ссылки те же, а
описывает релиз уже другой код. Protected tags мешают переставить тег
постороннему, но не владельцу проекта — а релизы делает как раз он.

Правило одно на оба режима: `Release.commit` обязано совпасть с фактическим
коммитом тега (`GET /projects/:id/repository/tags/:tag` → `commit.id`).
Расхождение значит, что релиз создавали на одном коде, а тег теперь указывает на
другой.

Сравнивать с `$CI_COMMIT_SHA` **нельзя**, и это не мелочь. В production они
совпадают (пайплайн идёт по тегу), а в смоуке — нет: тег `smoke` создаётся один
раз, а сам смоук запускается с `master`, который с тех пор ушёл вперёд. Правило
через `$CI_COMMIT_SHA` роняло бы каждый второй смоук при совершенно исправном
состоянии — то есть противоречило бы его же требованию идемпотентности.

Дополнительно **только в production**: коммит тега обязан совпасть с
`$CI_COMMIT_SHA`. Это ловит перезапуск старого пайплайна после перестановки
тега. В смоуке проверка не применяется — там пайплайн к тегу не привязан.

Описание релиза (`description`) задаётся только при создании и **не
сравнивается**: release notes правят руками осознанно, и перезаписывать их
повторным запуском публикации нельзя.

### Смоук против настоящего API (замечание 3)

Фейковый транспорт проверяет алгоритм, а не GitLab: формат ответа `/packages`,
коды ошибок реестра, работу `JOB-TOKEN`, приём `assets.links` при создании
Release и вид ссылки скачивания приватного пакета он не проверяет никак. Без
отдельного шага первый настоящий релиз стал бы одновременно интеграционным
тестом API — на артефактах, которые уже кто-то ждёт.

Поэтому — ручной job `release:smoke` (`publish_gitlab.py --smoke`), доступный на
`master` и при ручном запуске. Он повторяет **форму** production-релиза, а не
его упрощённую версию:

- **два файла, а не один**, с production-именами:
  `smartapp-dsl-0.0.0-smoke.zip` и `smartapp-dsl-0.0.0-smoke.vsix` (содержимое —
  несколько байт). Иначе API-сценарий не проверил бы ни двух `package_files`, ни
  двух `assets.links` — то есть ровно того, из чего состоит настоящий релиз;
- тег для Release — `smoke`, **не** `v<версия>`: под protected tags `v*` он не
  попадает, релизных правил не задевает и собственного пайплайна не создаёт
  (`workflow:rules` пропускают только semver-теги). Тег **создаёт Release API из
  `ref`** (ветка по умолчанию), отдельного push нет;
- **happy path** на фиксированной версии `0.0.0-smoke`: первый запуск проходит
  ветку «создать», второй — «уже есть, совпадает». Повторные запуски
  идемпотентны, мусор не растёт;
- **сценариев дублей два, и версии у них тоже две** — состояние версии
  необратимо, из «два разных хеша» обратно в «два одинаковых» без удаления файлов
  не вернуться:

  | Версия | Подготовка | Что проверяет |
  |---|---|---|
  | `0.0.0-smoke-dup-diff` | файл A, затем B с тем же именем и другим содержимым | публикация обязана упасть на несовпадении хеша |
  | `0.0.0-smoke-dup-same` | файл A дважды | публикация обязана пройти без `PUT` |

  Через идемпотентную публикацию дубль не появится никогда (второй запуск видит
  тот же хеш и не грузит), поэтому оба состояния создаются **намеренно прямыми
  `PUT`**, минуя алгоритм;
- **подготовка выполняется один раз за всё время, а не на каждый прогон, и
  только при точном совпадении состояния.** Перед тем как пропустить прямые
  `PUT`, смоук сверяет `package_files` версии с ожидаемым: число файлов, имя,
  полный набор хешей. Разбор случаев:

  | Фактическое состояние | Действие |
  |---|---|
  | совпало с ожидаемым | подготовка пропускается |
  | версия пуста | подготовка выполняется целиком |
  | ровно один файл с ожидаемым хешем | доливается недостающий |
  | что-либо иное (лишние файлы, чужие хеши, другое имя) | **FAIL**: версия требует ручной уборки, ничего не пишем |

  Без этого прерванный первый смоук оставил бы половину состояния, а следующие
  запуски молча проверяли бы не тот сценарий — то есть зелёный результат
  перестал бы что-либо значить;
- **мусор постоянен**: три версии пакета и один релиз, сколько бы раз смоук ни
  запускали. Версия на прогон (`…-$CI_PIPELINE_ID`) отвергнута именно поэтому —
  план предписывает гонять смоук после каждой правки скрипта, и реестр рос бы
  без предела. Токен с `api`-scope ради уборки не заводится: долгоживущий секрет
  в CI дороже трёх мусорных версий, а отдельный тестовый проект — это второе
  место, где всё придётся настраивать заново;
- **побочный результат, который иначе взять негде:** второй прямой `PUT`
  показывает, в каком режиме реестр. Прошёл — дубли разрешены (ожидаемо для
  личного namespace). Отказ с `400 Duplicate package is not allowed` — значит
  политика включена, и алгоритм обязан пройти через ветку «отказ → перечитать →
  сверить». Страницы групповых настроек у личного namespace нет, поэтому
  подтвердить режим можно только так;
- **итого в реестре:** `0.0.0-smoke`, `0.0.0-smoke-dup-diff`,
  `0.0.0-smoke-dup-same` и релиз `smoke`. Убрать их можно только вручную токеном
  с `api`-scope (`CI_JOB_TOKEN` пакеты удалять не умеет) — и незачем: набор не
  растёт.

Job запускается перед первым релизом и после каждой правки `publish_gitlab.py`.

**Контракт завершения (замечание 2).** Смоук — прогон сценариев, и его код
возврата отвечает на вопрос «повёл ли себя API так, как мы считаем», а не «все
ли запросы прошли успешно». Иначе ожидаемое падение красило бы job постоянно, а
`allow_failure: true` прятал бы настоящую поломку.

| Сценарий | Ожидание | Вклад в код возврата |
|---|---|---|
| Публикация на чистой версии | создано, два файла и два link'а | 0 при совпадении |
| Повтор публикации | ни одного `PUT`, релиз не переписан | 0 при совпадении |
| `…-dup-same`: дубли с одинаковым хешем | успех без `PUT` | 0 |
| `…-dup-diff`: дубли с разным хешем | **ошибка сверки хеша** | 0 — ожидаемое падение считается прохождением |
| Подготовка дубля отклонена политикой | реестр в режиме `Deny` | 0, помечается «неприменимо» и печатается как диагностика |
| Версия дублей в неожиданном состоянии | требуется ручная уборка | 1 |
| Что угодно иное | — | 1 |

«Иное» — это неожиданный код ответа, сбой авторизации, сеть, 5xx, а также
**успешная** публикация при разных хешах: последнее означает, что защита не
работает, и это худший из исходов. Каждый сценарий печатает строку
`PASS/FAIL/N/A` с причиной, поэтому лог читается за секунды.

`allow_failure: true` остаётся — он нужен, чтобы ручной job не держал пайплайн, —
но теперь красный смоук означает именно поломку. Это осознанный компромисс:
результат виден только тому, кто нажал кнопку, и в статусе пайплайна его нет.

### Тестовый контур публикации (замечание 7)

`tools/ci/test_publish_gitlab.py` — фейковый транспорт вместо сети, тридцать четыре
сценариев, обязательных до реализации (запуск —
`python3 -m unittest discover -s tools/ci -p test_publish_gitlab.py`: `unittest`
принимает имя модуля, а не путь, а discovery сама кладёт стартовый каталог в
`sys.path`, поэтому тест импортирует `publish_gitlab` напрямую):

| Сценарий | Ожидание |
|---|---|
| Пакета нет | выполняется `PUT` |
| Файл есть, SHA совпал | `PUT` не выполняется, шаг успешен |
| Файл есть, SHA другой | ошибка, `PUT` не выполняется |
| `PUT` вернул `409` (гонка) | повторное чтение, сверка SHA, успех при совпадении |
| `PUT` вернул `400 Duplicate package is not allowed` | то же: решает состояние, а не код |
| `PUT` вернул `400` по другой причине | ошибка: состояние после него неверное |
| Файл только на второй странице | найден, повторной загрузки нет |
| Два файла с одним именем, SHA одинаковый | успех без `PUT` |
| Два файла с одним именем, SHA разный | ошибка (реестр дубли разрешает) |
| Release отсутствует | создаётся с двумя ссылками |
| Release есть, ссылки те же | успех без записи |
| Release есть, ссылок больше/меньше/другие | ошибка |
| Release есть, ссылки те же, `commit` ≠ коммита тега | ошибка (тег переставили) |
| Режим смоука: коммит тега ≠ `CI_COMMIT_SHA` | не ошибка (пайплайн идёт не по тегу) |
| Production: коммит тега ≠ `CI_COMMIT_SHA` | ошибка (перезапуск после перестановки тега) |
| Режим смоука: релиз на одном коммите, тег переставлен | ошибка — сверка с тегом действует и без коммита пайплайна |
| Тег переставлен между чтением и `POST` | ошибка: созданный релиз проверяется сразу |
| `POST` принят, но сохранил не тот набор ссылок | ошибка |
| Релиз есть, тега нет | ошибка: сверять не с чем |
| Тег покрыт защитой | публикация идёт |
| Тег не покрыт защитой | отказ до единой загрузки в реестр |
| Список недоступен | отказ, ноль загрузок в реестр |
| Список читает отдельный токен настроек | публикация идёт |
| Правило `v*` на второй странице | найдено, публикация идёт |
| Правила нет ни на одной странице | отказ |
| Заголовок авторизации: job-токен по умолчанию, `PRIVATE-TOKEN` для токена настроек | проверяется на настоящем транспорте |
| `main` строит транспорт настроек из `SMARTAPP_API_TOKEN` | ровно один, с `PRIVATE-TOKEN`; артефакты грузит job-токен |
| `CI_API_V4_URL` указывает на чужой хост | отказ |
| `CI_PROJECT_PATH` указывает на чужой проект | отказ |
| `CI_API_V4_URL` пуст или не задан | отказ |
| `CI_PROJECT_PATH` пуст или не задан | отказ |
| Путь проекта в ссылках релиза | слэш закодирован (`group%2Frepo`) |
| `main`: требование защиты и чтение переменной из окружения | связывание проверено отдельно |
| Production: тег и коммит пайплайна согласны, релиз совпадает | успех без записи |

Шаг `test:publish` гоняется на обоих хостингах: Python есть везде, сеть не
нужна.

### Доступ к опубликованным файлам

Реестр наследует права проекта, а проект приватный: ссылки Release **не будут
анонимными**. Для внутреннего инструмента это и требуется; публичная раздача —
Marketplace/OpenVSX, отдельная задача бэклога.

Защита от случайного релиза: protected tag `v*`, проверка `contract:version` и
`workflow:rules`, при которых нерелизный тег не создаёт пайплайна.

## Этап 5 — настройки проекта (UI, не файл)

1. **gitlab.com:** верификация аккаунта для shared runner'ов; защита `master`;
   **protected tags `v*` — это не «на всякий случай», а единственный механизм
   неизменности релизного тега**: API не даёт создать релиз атомарно на
   конкретном коммите, поэтому от перестановки тега защищает только запрет на
   уровне проекта. Настройка обязана быть **фактически включена до первого
   релиза**, а не описана здесь: релизный job читает список защищённых тегов и
   отказывается публиковать, если тег не покрыт **или если список прочитать не
   удалось** (этап 4). Проверить можно тем же `release:smoke` — он печатает
   состояние отдельной строкой;
   **CI/CD → Variables → `SMARTAPP_API_TOKEN`** — project access token с
   областью `read_api`, флаги «Protect variable» и «Mask variable». Без него
   релизный job не сможет прочитать список защищённых тегов и откажется
   публиковать; job-токен для этого не годится. **Область видимости переменной —
   `release`, а не `*`**: со звёздочкой токен приходил бы в каждый job
   пайплайна, включая тесты, которые исполняют чужой код (зависимости npm и
   плагины Gradle). Ради этой области у job'ов `release` и `release:smoke`
   объявлен `environment: name: release` — иначе scope не с чем сопоставлять.
   Ограничение роли для pipeline variables (Settings → CI/CD → «Minimum role to use pipeline variables»)
   полезно как дополнительный рубеж, но публикация на него не опирается: адрес
   API и проект зафиксированы в коде;
   Settings → Merge requests → *Pipelines must succeed*;
   Auto-cancel redundant pipelines. Запрета дублей в реестре **в этом списке
   нет**: настройка групповая, а namespace личный (см. этап 4) — гарантию даёт
   скрипт, и подтверждается она `release:smoke`, а не галочкой в UI.
2. **Зеркалирование.** GitHub-репозитория пока нет (в remote'ах только `origin`
   и `gitverse`). Создать и настроить в GitLab Settings → **Repository →
   Mirroring repositories** push-зеркало (доступно на Free). PAT хранится **в
   настройках зеркала**, а не в CI/CD Variables. Токену нужен scope `repo` и,
   поскольку зеркалируется `.github/workflows/`, дополнительно **`workflow`** —
   без него push отклоняется. Следствие: MR живут только в GitLab, реальные
   триггеры GitHub — `push` и `workflow_dispatch`.
3. **GitVerse** остаётся третьим remote'ом без CI.

## Этап 6 — документация

  частичная проверка (без стороны IDEA и без интеграционного теста VS Code); что
  Kotlin-снимок проверяется внутри `test:idea`, а не на стадии `contract`; что

## Отложено отдельной задачей — модуль `:contract`

Подграф контракта платформы не касается: `ExportRules.kt` импортирует gson,
`SmartAppContract.kt` — только `SmartAppRefKind`, а тот не импортирует ничего.
Отдельный модуль, подключённый как `implementation(project(":contract"))` (тем
же механизмом, что уже работает для gson), сделал бы проверку снимка секундной,
вернул бы её в дешёвую стадию `contract` и позволил бы гонять на GitHub.

Риск: правится работающая упаковка, а тесты его не поймают — они идут по
runtime-classpath, где классы есть всегда, а в собранном zip их может не
оказаться; нужна проверка состава архива и ручная установка.

## Риски и неизвестные

1. **Состояние прошлых прогонов** из репозитория не видно; этап 0 существует для
   этого. Пока оно неизвестно, оценки времени job'ов — оценки.
2. **Тесты платформы под maven-сборкой.** Локально — GIGA IDE CE 2025.1, в CI —
   IntelliJ IDEA Community 2025.1. Разные сборки одной версии; расхождение
   проявится в `BasePlatformTestCase`.
3. **Стоимость `verifyPlugin` измерена и остаётся высокой.** С явным списком из
   двух IDE проверка занимает ~5 минут, а весь прогон — 13 м 31 с, потому что
   верхнюю IDE пришлось скачать; на runner'е холодными будут обе. Отказаться
   нельзя (решение 6), поэтому если счёт за минуты не сойдётся, вариантов два:
   проверять на MR только нижний край (а оба — на `master` и теге) либо реже
   гонять интеграционный тест VS Code. Оба уменьшают гарантии, поэтому решаются
   по числам, а не заранее.
4. **Один Gradle-job вместо трёх** удлиняет самый длинный путь пайплайна: тесты
   и верификатор идут последовательно. Wall-clock платится за compute-минуты
   сознательно — дефицитен тариф.
5. **Устаревший снимок `rules.json`** не останавливает VS Code-job'ы (см. «Что
   блокирует что»). Цена — минуты на редком сценарии, ловится локально.
6. **Список системных пакетов проверяется только прогоном.** Первый же показал
   пропуск: `xvfb-run` требует `xauth`, а он у `xvfb` в рекомендациях, которые
   `--no-install-recommends` не ставит. Чтобы список не пополнялся по одному
   пакету после каждого падения, он взят из зависимостей официального `.deb`
   VS Code — у него есть источник. На GitHub этот риск снят отказом от
   интеграционного теста, а не проверкой.
7. **Поведение настоящего API** — формат `/packages`, коды ошибок реестра,
   приём `assets.links`, права `JOB-TOKEN` — фейковым транспортом не
   проверяется; это закрывает `release:smoke`, и он обязан быть прогнан до
   первого релиза. Гонку под `resource_group` смоук не воспроизводит: она
   останется подтверждённой только рассуждением.
8. **Реестр разрешает дубли** и это не настраивается в личном namespace. Если
   кто-то зальёт файл руками мимо пайплайна, публикация упадёт с ошибкой сверки
   — сознательно: молча выбрать один из двух файлов хуже.
9. **Красный `release:smoke` не виден в статусе пайплайна** (`allow_failure`):
   его результат читает тот, кто нажал кнопку. Альтернатива — сделать смоук
   гейтом — означала бы, что сеть и чужой API решают, можно ли слить MR.
