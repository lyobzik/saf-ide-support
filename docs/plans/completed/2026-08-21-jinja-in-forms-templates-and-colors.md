## Почему это не было сделано в плане 2026-07-25

План [`docs/plans/completed/2026-07-25-form-fields-and-jinja.md`](completed/2026-07-25-form-fields-and-jinja.md)
писался, когда боевых образцов Jinja в репозитории не было — это зафиксировано в
самом плане (раздел «Риски», п. 1: «Нет боевых образцов Jinja — реальный
синтаксис (фильтры, `variables.*`, подобъекты) неизвестен. План сознательно
ограничивается `main_form.<field>`; при получении реальных файлов — отдельная
итерация расширения лексера»). Пять из шести причин — это **сработавшее
ограничение scope**, одна — **дефект**.

### 1. Семантика полей включается только в SCENARIO-файлах (сознательно)

`SmartAppFieldRef.targetFormOf` начинается с `if (fileKind != SCENARIO) return null`
(и то же в `vscode-extension/src/core/fieldRef.ts`). Модель плана: целевая форма —
та, на которую указывает top-level свойство `form` **сценария**. Случай «Jinja
внутри самой формы, где `main_form` — это и есть текущая форма» не моделировался:
в корпусе `shared/fixtures/jinja-form-fields/` все кейсы сценарные.

Следствие: строки 43, 47, 80, 149 `hello_form.json` не дают ни ссылки, ни
предупреждения — `targetFormOf` возвращает `null` ещё до разбора выражения.

### 2. Цепочки `main_form.<field>.<sub>` исключены (сознательно)

«Корректирующий цикл 3» плана ввёл проверку правой границы: если после имени поля
идёт `.`, кандидат отбрасывается целиком. Мотив был верный — у значений полей нет
схемы, и резолвить `.name` не во что. Но вместе с недоступным вторым сегментом
выброшен и **первый**, который резолвится прекрасно: `main_form.person.name` →
`person` есть в `fields`. Это и есть регрессия UX на строках 43 и 47.

### 3. Statement-теги `{% … %}` без семантики (сознательно)

План: «`{% … %}` — только лексическая подсветка; семантических ссылок и WARNING не
создаётся». В боевом файле именно там стоит `{% if main_form.person.name is
defined %}` — то есть исключено ровно то место, где пользователь ждёт навигацию.

### 4. Поправка: заявленного дефекта в лексере нет

При первом разборе я утверждал, что `SmartAppJinjaLexer.fieldCandidates` (Kotlin)
обрабатывает только первую интерполяцию литерала, а TS-порт — все, то есть
реализации разошлись. **Это неверно.** `fieldCandidates` действительно выходит
из цикла на первом `INTERP_OPEN`, но `collectFromInterp` в конце дописывает
результат рекурсией:

```kotlin
// Рекурсивно обрабатываем остальные интерполяции в литерале.
result += scanMoreInterps(text, tokens, j)
```

Проверено тестами (`fieldCandidateInSecondInterpolation`,
`fieldCandidatesFromEveryInterpolation`,
`statementTagBetweenInterpolationsDoesNotStopScan` — обе стороны зелёные с
первого прогона, без правок продуктового кода): поля резолвятся в каждой
интерполяции, реализации согласованы.

**Что дырка в корпусе всё-таки скрывала — дефект раннера IDEA.** Кейса с двумя
интерполяциями в одном литерале не было, и потому не всплывало, что
`SmartAppConformanceTest.resolveAt` резолвил **все** ссылки литерала, игнорируя
каретку, и лишь при пустом результате переходил к отбору по диапазону. Пока у
литерала была максимум одна ссылка на поле, это было незаметно; на литерале
`"{{ main_form.name }}-{{ main_form.age }}"` кейс на `name` получил бы в ответ и
`name`, и `age`. То есть сторона IDEA отвечала «за литерал целиком» и не
различала два вхождения — любое будущее расхождение реализаций по позиции ссылки
прошло бы мимо корпуса. Исправлено вместе с добавлением кейса.

### 5. Ссылок на файлы шаблонов нет в модели DSL

`"file": "experience_items_template.jinja2"` при `"type": "unified_template"` —
ссылка **на файл**, а вся сегодняшняя машинерия резолвит **имя → top-level ключ
JSON** через индекс определений. В контракте нет ни правила для свойства `file`
(`SmartAppSpecs.refRules` его не содержит), ни вида `TEMPLATE`
(`SmartAppRefKind` — только SCENARIO/FORM/ACTION/BEHAVIOR/FILLER/CLASSIFIER), а
`PathSpec.fileExtension = ".json"` вообще выводит `.jinja2` из числа DSL-файлов.
Это не дефект реализации, а **пробел в модели**: класс целей «файл» никогда не
проектировался.

### 6. Подсветка Jinja наследует бесцветные атрибуты

`SmartAppTextAttributes` задаёт fallback'и так:

| Ключ | Наследует | Цвет в Darcula (GIGA IDE CE 2025.1) |
|---|---|---|
| `SMARTAPP_JINJA_DELIM` | `BRACES` | `DEFAULT_BRACES` → `<value />`, цвета нет |
| `SMARTAPP_JINJA_VAR` | `IDENTIFIER` | `DEFAULT_IDENTIFIER` → `#a9b7c6` (обычный текст) |
| `SMARTAPP_JINJA_OP` | `DOT` | `DEFAULT_DOT` → `<value />`, цвета нет |
| `SMARTAPP_JINJA_FILTER` | `OPERATION_SIGN` | `DEFAULT_OPERATION_SIGN` → `<value />`, цвета нет |
| `SMARTAPP_JINJA_STRING` | `STRING` | `DEFAULT_STRING` → `#6a8759` |

(значения взяты из `DefaultColorSchemesManager.xml` внутри `lib/app.jar` установленной IDE)

Четыре из пяти атрибутов не имеют собственного цвета и рисуются цветом обычного
текста. При этом silent-аннотация **перекрывает** зелёный `#6a8759` строки JSON.
Итог хуже, чем отсутствие подсветки: фрагмент `{{ … }}` из зелёного становится
ровным `#a9b7c6` — это и есть «все символы белые». Плагин не поставляет
`<additionalTextAttributes>` и своей цветовой схемы (в `plugin.xml` есть только
`colorSettingsPage`), так что переопределить не из чего.

Тесты этого не поймали, потому что план требовал проверить лишь **присутствие**
пяти `TextAttributesKey` в `doHighlighting` — то есть что атрибут навешен, а не
что он виден.

В VS Code картина мягче, но тоже неполная: fallback-scope'ы из `package.json`
против дефолтной темы Dark Modern (= `dark_plus` → `dark_vs`) дают
`punctuation.section.embedded.smartapp` → `#569cd6`, `variable.other.smartapp` →
`#9CDCFE`, `support.function.smartapp` → `#DCDCAA`, а вот
`punctuation.accessor.smartapp` не совпадает ни с одним правилом дефолтных тем —
оператор `.` остаётся цветом текста. Своих дефолтов расширение тоже не везёт.

### 7. `.jinja2` — отдельный язык, вне архитектуры обеих реализаций

Обе реализации по определению строят «семантический слой поверх встроенного
JSON-парсера редактора». Отдельный файл шаблона — не JSON: `SmartAppFiles.kindOf`
вернёт `null`, расширение активируется на `onLanguage:json` и селектор провайдеров
— `{ language: "json" }`. VS Code не знает языка `jinja2` вовсе, поэтому файл
показывается как plain text — «всё белое» здесь буквально корректно.

### Этап 2. Видимая подсветка Jinja — **сделано**

**IDEA.** Плагин везёт свои схемы `resources/colorSchemes/SmartApp{Default,Darcula}.xml`,
подключённые через `additionalTextAttributes` в `plugin.xml`: у всех семи ключей
`SmartAppTextAttributes` явный `FOREGROUND`. Палитра взята из самих схем
платформы — оранжевый/навигационно-синий ключевых слов для разделителей и точки
(структура шаблона), фиолетовый полей для переменных, жёлтый функций (в светлой —
оливковый метаданных, потому что штатный цвет функции на белом нечитаем) для
фильтров, зелёный строк для строковых литералов Jinja.

Fallback-ключи в `SmartAppTextAttributes` переведены с бесцветных `BRACES`,
`DOT`, `OPERATION_SIGN` и «цвета обычного текста» `IDENTIFIER` на `KEYWORD`,
`INSTANCE_FIELD` и `METADATA` — они работают в темах, которые наши схемы не
наследуют.

**VS Code.** У `smartappJinjaOperator` добавлен запасной scope
`punctuation.section.embedded`: измерением по встроенным темам (Dark/Light Modern
и Dark/Light+) подтверждено, что `punctuation.accessor` не красит ни одна из них,
а остальные шесть типов токенов цвет получают.

**Проверки.** `SmartAppColorSchemesTest` рефлексией собирает ключи
`SmartAppTextAttributes` и требует для каждого запись с непустым `FOREGROUND` в
обеих схемах; тест манифеста требует, чтобы у каждого `SemanticTokenType` был
scope из списка «красят все встроенные темы». Обе проверки прогнаны мутацией:
удаление цвета и удаление запасного scope роняют их.

Автоматически проверяется наличие цвета, не его удачность — приёмка по
скриншотам (четыре темы) остаётся ручной.

### Этап 5. Ссылки на файлы шаблонов — **сделано**

**5.0. Правило резолва — по наблюдаемому соглашению, и это записано в коде.**
Ключа `file` в публичных исходниках `smart_app_framework` нет вовсе: репозиторий
sberdevices/smart_app_framework выгружен целиком, grep по всем `*.py` не находит
ни `"file"`, ни `FileSystemLoader`; `core/unified_template/unified_template.py`
знает только `type`/`template`/`loader`/`support_templates`. Значит правило
выведено **из раскладки эталонного приложения**, а не из исходников — так оно и
описано в комментарии к `SmartAppSpecs.fileRefRules`, в `AGENTS.md` и в README.

Открытые вопросы закрыты так:

| Вопрос | Решение | Основание |
|---|---|---|
| Входит ли расширение в значение | Да, значение — имя файла целиком; контракт ничего не достраивает | `"experience_items_template.jinja2"` и файл с тем же именем на диске |
| Вложенные пути | Допустимы (`nested/items.jinja2`) | дешевле поддержать, чем запретить; кандидат строится конкатенацией |
| Выход за пределы каталога (`..`, ведущий `/`, `\`) | Цели не даёт и **ошибкой не считается** | чем такое значение является — из данных не следует; молчание честнее ложной ошибки |
| Отсутствующий файл | WARNING «Не удаётся разрешить файл шаблона '<имя>'» на весь литерал | как остальные unresolved-диагностики |
| Динамическое имя (Jinja) | Ни ссылки, ни ошибки | тот же принцип, что у динамической `form` |

**5.1. Контракт.** Новая секция `fileRefRules` — `FileRefSpec(property,
ownerTypes, searchDirs)`; `searchDirs` просматриваются по порядку. Это
несовместимое изменение структуры: `SmartAppContract.VERSION` 2 → 3, синхронно
`const` в `rules.schema.json` и `EXPECTED_CONTRACT_VERSION` в `contract.ts`,
снимок перегенерирован.

Побочно вскрылось **четвёртое** место с версией: `scripts/verify-contract.mjs`
хранил собственную копию и уронил сборку уже после того, как три
задокументированных места были синхронизированы. Теперь скрипт читает версию из
`contract.ts`; правило «мест ровно три» записано в `AGENTS.md`.

**5.2. Резолв и диагностика.** IDEA — `SmartAppFileRefRules` (алгоритм) и
`SmartAppFileReference` (цель — `PsiFile`), поиск через `VirtualFile`
относительно корня набора; индекс не участвует, поэтому dumb-guard не нужен.
VS Code — ядро в файловую систему не ходит, поэтому индекс получил **реестр
не-DSL файлов набора**: адаптер регистрирует их по факту существования, не читая
содержимое, а `definitionsAt`/`diagnostics` резолвят кандидата по реестру.
Провайдер умеет отдать `Location` в начале файла, текст которого не хранится.

Кейс корпуса `shared/fixtures/template-file-refs/`: переход в файл, вложенный
путь, отсутствующий файл (WARNING), выход за пределы каталога (молча), чужой
`type` у владельца (молча, хотя файл существует).

**5.3. Вне этапа** (в backlog): Find Usages `.jinja2`-файла и переименование
шаблона — нужен обратный индекс по файловым целям.

### Этап 6. Подсветка внутри `.jinja2` — **решено: не поддерживаем**

Принят вариант A. Обе реализации живут поверх JSON-парсера редактора; свой язык
означал бы в IDEA полноценный лексер, а в VS Code — первый асимметричный
функционал, то есть отказ от паритета как инварианта проекта. Плагин даёт
**навигацию** в файл шаблона (этап 5), а раскрашивают сам шаблон
специализированные средства: в VS Code — любое расширение для Jinja, в IDE на
платформе IntelliJ — плагин с поддержкой Jinja2. Границы описаны в `README.md` и
в `vscode-extension/README.md`.

## Риски

1. **Новые ложные WARNING.** Этапы 3 и 4 включают диагностику там, где её не
   было. Если в бою встречается форма, в которой `main_form` указывает не на себя
   (наследование форм, композиция), появятся ложные предупреждения. Смягчение:
   на боевом проекте после Этапа 3 диагностик должно быть **ноль** — это
   проверяемый критерий приёмки, а не пожелание.
2. **Цвета — вкусовщина.** Автоматически проверяется только наличие цвета, не его
   удачность. Отсюда обязательные скриншоты в приёмке и четыре темы (тёмная и
   светлая с каждой стороны).
3. **Правило резолва шаблонов может оказаться сложнее** (настраиваемый путь,
   несколько корней). Этап 5.0 сделан отдельным шагом именно поэтому: пока
   правило не подтверждено по исходникам фреймворка, в контракт оно не попадает.
4. **Бамп `contractVersion`** ломает совместимость снимка: расширение с прошлой
   версией откажется работать с новым `rules.json` и наоборот. Это штатное
   поведение (fail-closed), но требует одновременной выкладки обоих артефактов —
   и попадает в release notes.
5. **Statement-теги — открытый синтаксис.** `{% … %}` вмещает произвольные
   выражения; расширяя туда семантику, легко начать резолвить то, что полем не
   является. Границы прежние (`main_form` + `.` + identifier, левая граница), и
   негативные кейсы корпуса на них обязаны остаться.

## Вне плана (в backlog)

Разбор `~/work/tmp/nlpf-test-project` вскрыл смежные пробелы модели, к трём
заявленным дефектам не относящиеся, но зафиксировать их стоит:

- **Не опознаются каталоги `requirements/` и `bundles/`.** Оба —
  `FolderRepository` во фреймворке (`tools/vendor/resources__init__.py:120,128`),
  то есть полноценные виды сущностей. В `SmartAppRefKind` их нет: `bundles.json`
  боевого проекта не индексируется вовсе, а `external`-ссылки на requirement'ы
  резолвиться не могут.
- **Не опознаются file-репозитории** `responses.json`, `history.json`,
  `last_scenarios_descriptions.json`,
  `preprocessing_messages_for_scenarios_settings.json`, `last_action_ids.json` —
  они лежат прямо в `static/references/` и по `PathSpec` не попадают ни в один
  вид (вид определяется подкаталогом).
- **Find Usages и rename файла шаблона** — нужен обратный индекс по файловым
  целям (см. 5.3).
- **Ссылки на bundle-ключи**: `{{ gender_sensitive_text('bundle_hello_scenario',
  'key_answer') }}` — аргументы функции внутри Jinja адресуют `bundles.json`.
  Требует и вида BUNDLE, и разбора аргументов вызова в лексере.
