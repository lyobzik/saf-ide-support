# Автодополнение имён файлов шаблонов

> **Статус:** выполнен 2026-08-21.
>
> Реализовано ровно то, что описано ниже; отклонений от решений нет, кроме
> одного уточнения по механизму обхода в IDEA (см. «Итоги»).
>
> Пройдено три раунда ревью плана; тринадцать замечаний закрыты решениями ниже.
> Два из них расширили объём: регистр путей и политика символических ссылок —
> это дыры в **резолве**, которые completion лишь делает заметными.
>
> Основание — замер автодополнения в обоих редакторах по просьбе владельца.
> Все ссылочные позиции контракта (`form`, `scenario`, `scenario_description`,
> `filler`, `classifier`, `action`, `behavior`), значения `type` и поля формы
> после `main_form.` предложения дают. Единственная позиция без предложений —
> `"file"` при `"type": "unified_template"`.

Поведение то же, проверено тестом с симлинк-циклом (снятие обрыва роняет тест) |

## Что наблюдается

Пишем `"file": "` и в VS Code получаем **16 случайных слов из документа**
(`answer`, `base`, `broken_scenario`, `fields`, `form`, `hello_form`, …) — это
word-based suggestions самого VS Code, которые включаются, когда ни один
провайдер ничего не предложил. В IDEA список пуст либо состоит из предложений
JSON-плагина платформы.

Переход в файл шаблона работает (`shared/fixtures/template-file-refs/`), а
дополнение имени — нет: правило `fileRefRules` используется резолвом и
диагностикой, но не автодополнением.

**Чего в замере не нашлось.** Остальные жалобы на автодополнение — не наши:

- в IDEA при непустом префиксе список не открывается, потому что платформа
  **авто-вставляет единственное совпадение** (в документе после вызова уже стоит
  дописанное значение). Контрольный замер с девятью подходящими именами на
  префикс `d` показывает все девять — префиксный матчинг исправен;
- в VS Code рядом с нашими вариантами встречаются варианты в кавычках
  (`"missing_form"`, `"form_filling"`) — это JSON-сервис редактора предлагает
  значения, уже встречавшиеся у того же ключа. Чужой провайдер отключить нельзя.

## Решения по объёму

| Вопрос | Решение | Почему |
|---|---|---|
| Что предлагать | Пути файлов относительно каталога поиска, вместе с расширением: `items.jinja2`, `nested/deep.jinja2` | Ровно то, что принимает резолв: значение — путь от каталога поиска, расширение контракт не достраивает |
| Откуда каталоги | `searchDirs` того же правила `SmartAppSpecs.fileRefRules` | Один источник для резолва, диагностики и completion — иначе они разъедутся |
| Несколько каталогов в правиле | Варианты — **объединение каталогов с дедупликацией по относительному пути**. Какой каталог «победит», решает резолв, а не completion | Значение в файле — путь без каталога, поэтому в предложенном варианте приоритета нет вовсе: пользователь вставляет `items.jinja2`, а какой из одноимённых файлов откроется, определяет `findFile` / `findFileByRelativePath` (первый существующий кандидат). Инвариант, который обязан держаться: **каждый предложенный путь резолвится** |
| Вложенные файлы | Предлагаются вместе с путём | Резолв их уже принимает; предлагать только верхний уровень значило бы скрыть половину каталога |
| Каталоги как варианты | Не предлагаются | Значение обязано указывать на файл; каталог целью не является |
| Нет каталога `templates` | Пустой список, без ошибки | То же, что при отсутствии файла: молчание, а не ложная диагностика |
| Значение с Jinja | Предложений нет | Динамическое имя — как и везде |
| Изоляция наборов | Предлагаются только файлы **своего** набора `references` | Та же изоляция, что у резолва и у имён сущностей (`SmartAppScopes`); в монорепо иначе предложится файл чужого приложения |
| Размер каталога | **Best-effort без гарантий производительности**: полный обход на каждый вызов, отменяемый; усечения нет | См. «Размер каталога» |
| Имена, требующие JSON-экранирования | Не предлагаются; предикат общий для двух реализаций и задан посимвольно | См. «Экранирование и координаты» |
| Регистр | Пути шаблонов **регистрозависимы** в обеих реализациях, во всех сегментах | См. «Регистрозависимость» |
| Символические ссылки | Следуются — и в резолве, и в completion; защита от циклов, а не запрет. Полного паритета нет: состав списка в VS Code зависит от `search.followSymlinks` | См. «Символические ссылки» — это осознанное исключение, а не единая политика |
| Готовность | Расширение молчит до `markReady()`, IDEA — нет | Источники разной природы, см. ниже |
| Контракт данных | Не меняется, `contractVersion` остаётся 4 | Каталоги уже в контракте; добавляется только алгоритм |

## Реализация

### Ядро расширения

`SmartAppIndex` уже хранит реестр не-DSL файлов набора (`assets`: путь → URI).
Нужен запрос «файлы каталогов правила»:

```ts
/**
 * Пути файлов внутри <referencesRoot>/<dir> для каждого dir, относительно
 * самого dir: объединение каталогов, одинаковый путь — один вариант.
 */
filesInDirs(referencesRoot: string, dirs: readonly string[]): string[]
```

Дедупликация живёт **внутри** этого метода, а список каталогов
приходит параметром — так двухкаталожный случай проверяется юнит-тестом, не
трогая общие данные контракта (в `rules.json` каталог сегодня один, и
подмешивать туда второй ради теста нельзя).

Изоляция набора получается из самого запроса: ключи реестра — пути, отбор идёт
по префиксу `<referencesRoot>/<dir>/`, а `referencesRoot` берётся у файла, в
котором стоит каретка.

`completion.ts` получает ветку до ссылочной: если узел стоит в позиции файловой
ссылки (`isFileReference` из `fileRefRules.ts`), варианты берутся из
`filesInDirs`. Диапазон замены — как у имён сущностей (`literalRange`): всё
содержимое литерала без кавычек, чтобы VS Code фильтровал по набранному
префиксу, включая `/`.

Новый `CompletionKind` — `"file"`. TS-раннер корпуса сверяет `kind`, поэтому
кейс зафиксирует и его.

**Готовность индекса.** Ветка молчит до `markReady()`, как ссылочная и как
Jinja-ветка: реестр `assets` наполняется в ходе первичного сканирования, и
частичный список — это список, который через секунду молча изменится под
пользователем. Пустой результат честнее.

### Плагин IDEA

Индекса для этих файлов нет (резолв идёт по `VirtualFile`), поэтому completion
обходит каталог: `SmartAppFiles.referencesRoot(originalFile.virtualFile)` →
`findChild(dir)` → обход, только файлы, путь относительно каталога. Обход — от
`originalFile`, а не от копии: у in-memory копии реального пути нет (та же
причина, по которой `fileKind` передаётся снаружи).

Сбор выносится в отдельный объект с той же сигнатурой, что в ядре:
`SmartAppTemplateFiles.pathsIn(root: VirtualFile, dirs: List<String>): List<String>`
— дедупликация внутри, список каталогов параметром.
У функции ровно один вызывающий: ветка completion передаёт в неё
`SmartAppFileRefRules.searchDirs(literal)` целиком, без индексации и `first()`.

Префикс задаётся явно: `result.withPrefixMatcher(<decoded-текст литерала до
каретки>)`. Без этого платформенный матчер ломается на `/` в пути и вложенные
файлы перестают совпадать. `withTypeText("file")`.

**Готовность индекса здесь не при чём.** Источник — VFS, а не `FileBasedIndex`,
поэтому dumb-guard ветке не нужен: во время индексации она отдаёт **полный**
список, как и ветка ключевых слов `type`. Это осознанная асимметрия с
расширением, где источник действительно неполон до конца сканирования; она
закрепляется тестами с обеих сторон, чтобы не выглядеть случайной.

### Размер каталога

Из трёх вариантов (best-effort, лимит, кэш с VFS-инвалидацией) выбран
**best-effort, объявленный явно**: ветка не даёт гарантий по времени и по числу
вариантов, стоимость — O(файлов в каталогах правила) на вызов.

- **Лимит отвергнут не из лени.** Усечённый список ломает не производительность,
  а корректность: платформы фильтруют по префиксу уже собранный набор, поэтому
  выброшенный файл не появится и после того, как пользователь наберёт его имя
  целиком. «Файла нет в списке, хотя он есть на диске» — худший из трёх исходов.
  Детерминированное усечение (сортировка, затем первые N) эту проблему не
  решает, а только делает её одинаковой в двух реализациях.
- **Кэш отвергнут:** это второй источник правды, ему нужна инвалидация по
  событиям VFS, а промах в сторону устаревания (предложить удалённый шаблон,
  скрыть новый) хуже стоимости обхода каталога из десятка файлов.
- **Что делается вместо гарантии:** `ProgressManager.checkCanceled()` на каждом
  шаге обхода (completion идёт в своём потоке под read action, но без явной
  проверки обход не прервётся при наборе следующего символа) и обрыв цикла по
  каноническому пути каталога. Платформенный `VfsUtilCore.visitChildrenRecursively`
  не подошёл: у его опций нет варианта «следовать ссылкам, но не проходить один
  каталог дважды», а согласована именно такая политика. В расширении обход — это
  фильтрация in-memory реестра, ввода-вывода нет вовсе.
- Пункт «снимок каталога с инвалидацией по VFS-событиям» уходит в
  `docs/plans/backlog.md` как известное ограничение с направлением решения.

### Экранирование и координаты

Резолв работает с decoded-значением литерала, а фильтрация в редакторе — с
сырым текстом документа. Чтобы координаты не разъезжались, предлагаются только
пути, которые в JSON пишутся без экранирования. Предикат — **общий контракт двух
реализаций**, задан посимвольно:

> Путь предлагается, если ни один его символ не является кавычкой `"` (U+0022),
> обратным слэшем `\` (U+005C) или управляющим символом с кодом строго меньше
> U+0020. Всё остальное разрешено, включая любые не-ASCII символы.

Ровно эти три класса JSON обязывает экранировать; для всех остальных имён
decoded-текст совпадает с raw, и метка, вставляемый текст и префикс живут в одной
системе координат. Имя с `\` и так не резолвится (`isSafeRelativePath` его
отвергает), а строить экранированный `insertText` ради имени с кавычкой в v1 не
будем.

Одинаковость предиката фиксируется тестами с **одной и той же таблицей входов**
в обеих реализациях:

| Вход | Ожидание | Что проверяет |
|---|---|---|
| `items.jinja2` | предлагается | базовый случай |
| `привет.jinja2` | предлагается | не-ASCII экранирования не требует |
| `q".jinja2` | не предлагается | кавычка |
| `back\slash.jinja2` | не предлагается | обратный слэш |
| `bell<U+0007>.jinja2` | не предлагается | управляющий символ |

Тесты — на самом предикате, а не через файловую систему: файл с управляющим
символом в имени создаётся не на всякой ФС, и кейс корпуса был бы
непереносимым. В корпус попадает только то, что создаётся везде.

**Остаточное ограничение.** Префикс для матчера IDEA берётся из decoded-текста
тем же декодером, что и в ветке полей, поэтому вручную набранный escape
(`\u043f` вместо самой буквы) в IDEA сопоставится с меткой, а в VS Code — нет: он
фильтрует по сырому тексту диапазона. Это записанное ограничение, а не
недосмотр; ради ручного `\u`-escape в имени файла второй `filterText` не строим.

### Регистрозависимость

Сегодня стороны расходятся, и это не связано с completion: реестр расширения
сравнивает пути точно, а `VirtualFile.findFileByRelativePath` на
регистронезависимой ФС (macOS) находит `items.jinja2` по значению
`Items.JINJA2`. Значит, диагностика «Не удаётся разрешить файл шаблона» зависит
от файловой системы разработчика — на Linux-CI она есть, на Mac её нет.

- `SmartAppFileRefRules.resolve` идёт по сегментам пути (`findChild`) и сверяет
  фактическое имя каждого сегмента с запрошенным посимвольно; несовпадение
  регистра **в любом сегменте** = цель не найдена;
- расширение не меняется — оно уже регистрозависимо;
- кейсы корпуса — два, и второй нужен именно потому, что первый проходит и при
  сверке одного лишь последнего сегмента:
  - `"Items.JINJA2"` при существующем `items.jinja2` — целей нет, предупреждение
    есть;
  - `"Nested/deep.jinja2"` при существующем `nested/deep.jinja2` — то же самое
    (ошибка в промежуточном каталоге).

Регистр в **фильтрации** списка контрактом не объявляется: матчинг префикса
делают сортировщики платформ (в IDEA — настройка «Case sensitive completion»),
и корпус, как и раньше, ставит каретку в позицию с пустым префиксом.

### Символические ссылки

**Что действительно одинаково** — внутри каждой реализации политика едина для
резолва и для completion: ссылки следуются, запрета нет, цикл не вешает обход.

- файл-ссылка резолвится и предлагается: у неё есть имя в каталоге, она
  открывается, и отказ сломал бы законную раскладку (общие шаблоны, слинкованные
  в набор);
- в каталог-ссылку обход **заходит**, но платформенный обход IDEA ограничивает
  повторное прохождение ссылок, поэтому цикл не даёт бесконечной рекурсии;
- резолв не меняется вовсе.

**Полного паритета между реализациями здесь нет — это осознанное исключение.**
Плагин IDEA следует ссылкам всегда; в VS Code состав реестра определяет
`workspace.findFiles`, а он подчиняется настройке редактора
`search.followSymlinks` (по умолчанию включена). При выключенной настройке файлы
под каталогом-ссылкой не попадут ни в completion, ни в резолв расширения, а в
IDEA останутся. Совпадение поведения гарантируется только при настройке по
умолчанию.

Формулировка «одна политика в обеих реализациях» была бы неверна, поэтому
исключение записывается там, где его прочитают до того, как оно удивит:
`AGENTS.md` (раздел про файловые ссылки), `vscode-extension/README.md` (рядом с
описанием перехода в шаблон) и `docs/plans/backlog.md` — как и любое известное
расхождение.

**Почему не полный запрет** (второй вариант ревью). Расширение о ссылках не
знает: реестр наполняется по glob `**/static/references/**/*`, а `stat`
вызывается ради факта существования; информации о том, что промежуточный каталог
— ссылка, в реестре нет, и получить её без посегментного `stat` на каждый
кандидат нельзя. Запрет, реализованный только в IDEA, дал бы расхождение при
настройках по умолчанию, то есть у всех, — вместо расхождения у тех, кто
осознанно выключил следование ссылкам в поиске.

### Заметка в корпусе

`shared/fixtures/README.md` объясняет требование «каретка в позиции с пустым
префиксом» тем, что «IDEA отфильтрует список своим prefix matcher'ом». Замер
показал другое: матчер работает, а список не открывается из-за **авто-вставки
единственного совпадения** — и раннер IDEA это уже учитывает
(`lookupElementStrings ?: … ?: insertedIdentifier()`). Совет остаётся верным,
обоснование надо заменить, иначе следующий кейс будут писать под несуществующую
причину.

## Проверка

### Корпус

- **Новая фикстура `template-file-completion`** — два набора, `app_a` и `app_b`,
  у каждого свой `templates`:
  - `app_a`: `items.jinja2`, `nested/deep.jinja2`, `shared.jinja2`;
  - `app_b`: `shared.jinja2`, `only_b.jinja2`;
  - completion в `app_a` (каретка сразу после открывающей кавычки пустого
    значения `"file"`): `items.jinja2`, `nested/deep.jinja2`, `shared.jinja2`;
    в `absent` — `only_b.jinja2` (чужой набор), `nested` (каталог), `forms.json`
    (DSL-файл набора);
  - симметричная проверка в `app_b`: `only_b.jinja2` есть, `items.jinja2` нет.
  Одноимённый `shared.jinja2` в обоих наборах нужен затем, чтобы утечка не
  маскировалась совпадением имён.
- **`template-file-refs`**: добавляются ссылки `"Items.JINJA2"` и
  `"Nested/deep.jinja2"` — целей нет, предупреждения есть.

### Тесты ядра расширения

Пустой префикс; префикс с `/`; отсутствующий каталог; значение с Jinja; **два
каталога** вызовом `filesInDirs` напрямую — объединение с дедупликацией
(одинаковый путь ровно один раз) и инвариант «каждый предложенный путь
существует хотя бы в одном из перечисленных каталогов» (ловит и чужую базу пути,
и просочившийся каталог);
**два набора в одном индексе** (файл чужого набора не предлагается); **до
`markReady()` — пусто**; таблица предиката JSON-safe (пять входов выше).

### Тесты плагина IDEA

Те же случаи через `completeAt`; вложенный путь целиком; **два каталога** —
прямым вызовом `SmartAppTemplateFiles.pathsIn(root, listOf("templates", "partials"))`
на фикстуре с обоими каталогами: те же два утверждения, что и в ядре (симметрия
с TS-тестом, которой в прошлой редакции плана не было); **dumb mode** — список полон (фиксирует осознанную
асимметрию с расширением); таблица предиката JSON-safe — те же пять входов;
регистр — через кейсы корпуса.

### Сквозная передача каталогов

Требование «completion передаёт **все** `searchDirs`, а не первый» сегодня
непроверяемо поведением: в контракте у правила один каталог, и слайс `first()`
дал бы тот же результат. Подделывать данные контракта ради теста нельзя, поэтому
защита строится иначе — **fail-closed сторож**: тест утверждает, что у каждого
правила `fileRefRules` ровно один каталог поиска. Появится второй — тест
покраснеет и потребует добавить сквозной кейс корпуса вместе с ним. До тех пор
гарантию даёт форма кода: единственный вызывающий передаёт список целиком, а вся
логика нескольких каталогов живёт в функции, которую с обеих сторон тестируют
двумя каталогами напрямую.

### Адаптер и живой редактор

- **Адаптер VS Code**: `CompletionItem` с корректным диапазоном замены (ошибку
  диапазона корпус не увидит — он проверяет состав, а не то, что вставится).
- **Живой редактор**: smoke-кейс в `test/integration` — в позиции `"file"`
  список содержит `items.jinja2` (сейчас там 16 посторонних слов).

### Мутации

Убрать дедупликацию → падает тест двух каталогов (обе стороны); собрать пути
относительно корня набора, а не каталога поиска → падает инвариант «путь
существует в одном из каталогов»; снять фильтр по
`referencesRoot` → падает кейс изоляции; сверять только последний сегмент пути →
падает кейс `"Nested/deep.jinja2"`; убрать сверку регистра вовсе → падает
`"Items.JINJA2"` (на macOS); убрать гейт готовности в ядре → падает тест «до
`markReady()` пусто».

## Риски и осознанные ограничения

1. **Нет гарантии по размеру каталога** — принято сознательно (см. «Размер
   каталога»), с записью в бэклог.
2. **Асимметрия источников.** VS Code берёт файлы из реестра индекса, IDEA — из
   VFS. Наборы обязаны совпадать; расхождение поймает только кейс корпуса,
   поэтому он обязателен.
3. **Асимметрия готовности.** До конца сканирования расширение молчит, IDEA
   отдаёт полный список. Это следствие разной природы источников, а не разной
   семантики; закрепляется тестами с обеих сторон.
4. **Авто-вставка в IDEA.** При единственном шаблоне список не покажется —
   значение допишется сразу. Штатное поведение платформы, раннер корпуса его уже
   учитывает; в фикстурах шаблонов не меньше трёх файлов.
5. **Ручной `\u`-escape в значении** гасит фильтрацию в VS Code.
6. **`search.followSymlinks`** в VS Code меняет состав реестра, а значит и
   список вариантов; плагин IDEA от настройки редактора не зависит.
