# Монорепозиторий: плагин для IDEA + расширение для VS Code

Статус: **реализовано** 2026-08-20.

## Контекст

Репозиторий содержал одну реализацию поддержки DSL `smart_app_framework` —
плагин для IntelliJ-платформы. Требовался паритетный опыт редактирования тех же
файлов `static/references/**/*.json` в VS Code, без потери качества уже
работающего плагина.

Вариант «один LSP-сервер на обе IDE» отклонён: встроенный LSP-API IntelliJ
доступен только в Ultimate-редакциях, а целевая IDE — GIGA IDE CE. Путь через
сторонний LSP4IJ означал бы переписывание работающего плагина, потерю
PSI-нативных Find Usages / rename / dumb-mode и требование Node у пользователей
IDEA.

Решение: **две нативные реализации, связанные двумя контрактами**.

## Принятые решения

| # | Решение |
|---|---|
| 1 | `shared/rules/rules.json` — генерируемый снимок Kotlin-таблиц, руками не редактируется |
| 2 | `src/core` расширения не знает ни о `vscode`, ни о файловой системе; адаптер владеет `findFiles`/watcher'ами |
| 3 | Строгость JSON применяется **только к вкладу файла в индекс** — как в плагине, где `JsonPsi.hasError` вызывается лишь индексаторами |
| 4 | Поведение платформы на комментариях и висячих запятых **измерено**, а не угадано |
| 5 | `contractVersion` — только у `rules.json`; словарь проверяется схемой и `--check` генератора |
| 6 | Платформа сборки переключается свойством `ideSource=local\|maven`; CI — GitLab |
| 7 | Conformance-корпус общий; ID определения — `file + name + ordinal`; ожидания содержат диапазоны |
| 8 | Корпус гоняется на трёх уровнях: Kotlin, ядро TS, адаптер TS (+ smoke в живом VS Code) |
| 9 | Все DSL-имена приходят из контракта через единственный модуль `contract.ts` |
| 10 | Схемы валидирует одна проверка — AJV в CI; JSON-Schema-валидатор в плагин не тянем |

## Что сделано

- **Контракт данных.** Правила ссылок, ключи контекста `type`, структурные
  ключи, сегменты пути, `form`/`fields`, `main_form` вынесены во внутренние
  Kotlin-таблицы (`contract/SmartAppContract.kt`), которые использует и рантайм,
  и экспортёр. Таск `:idea-plugin:exportRules` (с режимом `--check`) пишет снимок
  в `shared/rules/rules.json`.
- **Словарь** переехал в `shared/keywords/`, генератор получил `--check`,
  а `SmartAppKeywords` — fail-fast вместо тихого `emptyMap()`.
- **Перенос** плагина в `idea-plugin/` git-aware переименованием; имя артефакта
  сохранено (`smartapp-dsl-<версия>.zip`) через `intellijPlatform.projectName`.
- **Расширение VS Code**: ядро (`src/core`) — порт семантики без единого импорта
  `vscode`; адаптер (`src/vscode`) — провайдеры, watcher, трансляция смещений.
- **Corpus** `shared/fixtures` — 14 кейсов, прогоняются Kotlin-тестом и двумя
  уровнями TS-тестов.
- **CI** `.gitlab-ci.yml`: стадия `contract` (снимок, словарь, схемы) блокирует
  стадию `test` (плагин, ядро+адаптер, VS Code под xvfb).

## Что показала проверка

- **Комментарии и висячие запятые не являются ошибкой** для JSON PSI IntelliJ:
  файлы с ними индексируются. Это выяснено характеризационными тестами до порта
  (предположение в плане было обратным) и определило настройки `jsonc-parser`.
- **Корпус поймал реальное расхождение**: ядро расширения создавало ссылку на
  поле формы для Jinja в *ключе* JSON, тогда как плагин ссылок на ключи не даёт.
  Исправлено проверкой `isValueNode`.
- **Границы контракта уточнены**: порядок имён в индексе и порядок вариантов
  автодополнения задают сортировщики платформ, поэтому корпус фиксирует состав,
  а не последовательность.
- **Интеграционный прогон нашёл дефект адаптера**: файл, открытый во время
  первичной индексации, больше не получал предупреждений. Добавлен пересчёт по
  `onDidChangeVisibleTextEditors`.

## Второй раунд ревью: что доработано

| Проблема | Решение |
|---|---|
| Интеграционный прогон не собирал бандл (в чистом CI `out/` нет) | `test:integration` теперь начинается с `npm run compile` |
| Поиск файлов игнорировал `extensionIgnoreCase` из контракта | glob строится из `paths.rootSegments` без расширения, отбор делает `isDslFile`; `workspaceContains` тоже не привязан к регистру |
| Jinja в JSON-ключе попадала в обратный индекс — переименование поля правило ключ | в `collectUsages` добавлен value-guard; покрыто repro-тестом |
| Rename неоднозначной ссылки молча выбирал `ACTION` | вид определяется по фактически найденным определениям; при нескольких видах rename отклоняется с объяснением (`renameLookupAt.reason`) |
| `fieldsProperty` и соответствия «ключ → категория» дублировались в коде | перенесены в контракт (`typeContext.keyCategories`, `insideFieldsCategories`), `contractVersion` поднят до 2 |
| `verifyPlugin` был заведомо красным | в `<description>` добавлен английский вводный абзац; верификатор: **Compatible** против 5 версий IDE |

Дополнительно найдено при проверке и исправлено:

- **Kotlin-раннер молча пропускал секции `references` и `rename`**, хотя фикстуры
  их объявляли: сторона IDEA не проверяла часть контракта. Обе секции
  реализованы, добавлен guard `testEverySectionIsSupported` — неизвестная секция
  теперь валит тест, а не игнорируется.
- **Диапазон использования** приведён к поведению IDEA: ссылка покрывает имя без
  кавычек (`rangeInElement`), диагностика — литерал целиком.
- Выяснено, что `myFixture.findUsages` подмешивает текстовые вхождения и
  одноимённые JSON-ключи из других файлов (поведение JSON-плагина платформы);
  раннер фильтрует результат до настоящих ссылок.

## Третий раунд ревью

| Проблема | Решение |
|---|---|
| `verifyPlugin` не был CI-gate — регрессия в `plugin.xml` дошла бы до master | отдельная обязательная job `test:idea:verify` с артефактом отчёта при падении |
| Проверка rename в IDEA-раннере была слабой: «строка содержит новое имя» | сравнивается содержимое **всех** файлов фикстуры с ожидаемым; лишняя правка, правка не того вхождения или постороннего файла валят тест |
| Usages отбирались по типу элемента, а не по принадлежности плагину | отбор по наличию `SmartAppReference`/`SmartAppFieldReference` на диапазоне usage (`usage.reference` для наших usages равен `null`, а платформа приносит свой `JsonPropertyNameReference`) |
| `includeDeclaration` из фикстуры IDEA-раннер игнорировал | поддержан, добавлен кейс с `includeDeclaration: true` |
| Гонка: watcher регистрировался после первичного сканирования | подписка выполняется до `findFiles`, плюс подхват уже открытых несохранённых документов; закреплено двумя adapter-тестами |

Найдено при проверке этих правок:

- **`shared/` не был входом задачи `test`**: Gradle считал тесты актуальными
  после правки фикстур, и мутационная проверка «зеленела» на устаревшем
  результате. Каталог объявлен входом (`inputs.dir`), после чего мутация
  фикстуры честно валит `testRename`.

Строгость новых проверок подтверждена мутациями: удаление правки из ожиданий
роняет `testRename` с точным diff, а возврат прежнего порядка подписки роняет
оба теста гонки.

## Четвёртый раунд ревью

| Проблема | Решение |
|---|---|
| TS-раннер игнорировал неизвестные секции корпуса | добавлен `SUPPORTED_SECTIONS` и тест, симметричный `testEverySectionIsSupported` |
| Позиция описывалась парой «строка + текст» — два одинаковых имени на строке неразличимы | введена колонка: опциональна, но **обязательна** при неуникальном вхождении, иначе оба раннера падают с требованием уточнить. Добавлена фикстура `same-line-duplicates` с двумя ссылками в одной строке |
| Гонка «старое чтение затирает свежее» после переноса watcher'а | у каждого URI есть номер поколения; результат чтения применяется, только если его никто не обогнал |
| `activationEvents` дублировал `static/references` вне контракта | оставлен только `onLanguage:json` — все функции и так работают лишь в открытом JSON; тест `activation.test.ts` запрещает возвращать путь в манифест |

Найдено при проверке этих правок:

- Первая версия теста гонки была **бессмысленной**: порядок чтений в моке
  оказался обратным задуманному, и тест проходил без защиты. Мок научился
  сообщать о начале чтения, тест стал детерминированным — и теперь честно
  краснеет без generation token.
- Применение ожидаемых правок в rename ломалось на нескольких заменах в одной
  строке (колонки смещались) — правки применяются снизу вверх и справа налево.
- Rename в IDEA переформатирует затронутый фрагмент: фикстура записана в
  каноническом для платформы стиле, иначе строгое сравнение содержимого падало
  бы на пробелах.

## Пятый раунд ревью

| Проблема | Решение |
|---|---|
| Kotlin rename-тест сравнивал только файлы своей фикстуры | сравниваются файлы **всех** фикстур проекта: чужие обязаны остаться нетронутыми. Добавлен rename-кейс в `scope-isolation` |
| Автоматическая активация не проверялась (тесты звали `activate()` вручную) | integration-smoke убеждается, что до открытия JSON расширение неактивно, и дожидается активации самим VS Code |

### Найден и исправлен дефект продукта

Расширенная проверка сразу поймала протечку: **переименование определения
переписывало одноимённые определения в чужих наборах `static/references`** — в
монорепозитории это порча соседнего приложения. Причина платформенная: JSON-плагин
связывает одноимённые ключи разных файлов (`JsonPropertyNameReference`), и штатный
рефакторинг обновлял их заодно.

Добавлен `rename/SmartAppRenameProcessor`: он ограничивает область
переименования ссылками плагина внутри набора `references` самого определения —
той же изоляцией, что уже действовала для резолва и диагностики. Регрессия
закреплена тестом `testRenameDoesNotLeakIntoOtherReferenceSets`.

Попутно выяснилось, что первая версия этого теста ничего не проверяла: она читала
файлы с диска (`contentsToByteArray`), а правки рефакторинга живут в документах.
После перехода на чтение через PSI мутация подтвердила: без процессора тест
краснеет с `"renamed_form"` в чужом наборе.
