# Бэклог SmartApp DSL

Идеи и осознанные ограничения, которые не входят в текущий объём работ, но
должны быть на виду. Каждый пункт — с причиной, чтобы решение можно было
пересмотреть осознанно.

## Поддержка JSONC и битого JSON — синхронно в обеих IDE

**Что сейчас.** Строгость применяется только к вкладу файла в индекс:
файл даёт определения, если распарсился без ошибок, его корень — объект и после
корня нет значимого хвоста (`JsonPsi.hasError` в индексаторах плагина,
`indexGate.ts` в расширении). Подсветка, ссылки, диагностика и автодополнение
работают и на битом файле — это поведение IDEA, и расширение его повторяет.

Комментарии и висячие запятые **не** считаются ошибкой: так ведёт себя JSON PSI
IntelliJ, и это зафиксировано характеризационными тестами
(`SmartAppStrictJsonContractTest`) и conformance-фикстурой `strict-json-indexing`.
`jsonc-parser` в расширении вызывается с теми же допущениями.

**Чего нет.** Файлы `*.jsonc` не обрабатываются вовсе: расширение активируется
только на языке `json`, а `SmartAppFiles` принимает только `.json`.

**Что потребуется, если решим поддержать.**

- IDEA: расширить `InputFilter` индексаторов и `SmartAppFiles`, пересмотреть
  strict-guard, поднять версии индексов (`getVersion()`), переписать тесты
  группы J1–J11 в `SmartAppIndexTest`.
- VS Code: добавить `onLanguage:jsonc` и расширение `.jsonc` в контракт
  (`paths.fileExtension` перестанет быть одним значением — это несовместимое
  изменение структуры, значит `contractVersion` придётся поднять).
- Общее: новые фикстуры в `shared/fixtures`, иначе две реализации разъедутся.

**Почему не сейчас.** Ни одного реального `.jsonc` в наборах `static/references/`
фреймворка не встречается; изменение затрагивает формат контракта и версии
индексов, то есть стоит дороже, чем приносит.

## Прочее

- **Второй сегмент цепочки** (`main_form.person.name`) семантики не получает:
  первый сегмент — поле формы и резолвится, а `name` — атрибут значения, которое
  положил filler. В `static/references/` такого объявления нет вовсе, прыгать
  некуда, и по той же причине не ставится WARNING. Понадобится — придётся
  связывать тип филлера с Python-классом фреймворка, то есть выйти за пределы
  «семантического слоя над JSON». Отдельный дешёвый вариант: если в проекте есть
  соглашение «тип филлера → фиксированный набор атрибутов», его можно внести в
  контракт таблицей. `main_form` в позиции чужого поля (`variables.main_form.x`)
  семантики не получает сознательно.
- **Виды `requirements` и `bundles`** не смоделированы, хотя во фреймворке это
  полноценные `FolderRepository` (`tools/vendor/resources__init__.py:120,128`):
  `bundles.json` не индексируется, `external`-ссылки на requirement'ы не
  резолвятся. Туда же — file-репозитории `responses.json`, `history.json`,
  `last_scenarios_descriptions.json`,
  `preprocessing_messages_for_scenarios_settings.json`, `last_action_ids.json`:
  они лежат прямо в `static/references/`, а вид определяется подкаталогом.
- **Ссылки на bundle-ключи**: `{{ gender_sensitive_text('bundle_hello_scenario',
  'key_answer') }}` адресует `bundles.json`. Требует и вида BUNDLE, и разбора
  аргументов вызова в лексере.
- **Find Usages и rename файла шаблона** (`"file"` при `unified_template`): цель
  — файл, а обратного индекса по файловым целям нет. Переход работает, обратное
  направление — нет.
- **Подсветка внутри `.jinja2`-файлов** не поддерживается сознательно: обе
  реализации — слой поверх JSON-парсера редактора, свой язык означал бы в IDEA
  полноценный лексер, а в VS Code — первый асимметричный функционал. Раскрашивают
  шаблон сторонние средства; переход в файл работает независимо от них.
- **Поля с не-identifier именами** (`odd.field`) не предлагаются в автодополнении
  и не резолвятся из Jinja: синтаксис доступа к ним в шаблонах нужно
  спроектировать отдельно.
- **Размер каталога шаблонов** в автодополнении не ограничен: список собирается
  на каждый вызов (обход VFS в IDEA, фильтрация реестра в расширении). Лимит не
  вводится сознательно — платформы фильтруют по префиксу уже собранный набор, и
  усечённый список навсегда спрятал бы существующий файл. Понадобится — правильный
  ответ не лимит, а снимок каталога с инвалидацией по событиям VFS.
- **Следование символическим ссылкам** совпадает у двух реализаций только при
  настройках по умолчанию: состав файлов в VS Code даёт `workspace.findFiles`,
  подчиняющийся `search.followSymlinks`, а плагин IDEA следует ссылкам всегда.
  Симметричный запрет не реализуем дёшево: в реестре расширения нет информации о
  том, что промежуточный каталог — ссылка, без посегментного `stat` на каждый
  кандидат.
- **Категории `operator`, `comparator`, `sdk_item` не имеют контекста позиции.**
  `TypeContextSpec` не выдаёт их ни по структурному ключу, ни по виду файла,
  поэтому слова этих категорий — и фреймворковые, и зарегистрированные
  приложением — не подсвечиваются и не предлагаются там, где категория
  определяется как другая. Задача про контекст `type`, а не про ресурсы
  приложения: нужны позиции в `typeContext.keyCategories` и кейсы корпуса.
- **Наборы `static/references` внутри зависимостей.** Плагин индексирует и
  резолвит DSL-файлы где угодно, включая `venv/lib/.../static/references`: для
  Find Usages кастомных слов такие кандидаты отсекаются списком исключённых
  сегментов, а определения и ссылки в остальных функциях по-прежнему туда ходят.
  Решать это стоит целиком — фильтром на уровне `SmartAppFiles`/скоупов, с
  кейсами корпуса, а не точечно.
- **Индекс использований `(категория, имя)` для Find Usages.** Сейчас handler
  обходит JSON-файлы приложения по PSI: одного источника правды достаточно, а
  версии индекса не нужно. Если обход окажется медленным на больших наборах,
  правильный ответ — обратный индекс, а не сужение области поиска.
- **Публикация расширения** в Marketplace/OpenVSX не настроена — как и публикация
  плагина IDEA в Marketplace. Обе стороны ставятся из артефакта (`.vsix` и
  `.zip`): GitHub выкладывает их в Release (скачиваются анонимно), GitLab — в
  реестр пакетов проекта (для участников). Это следующий шаг CD: понадобятся
  токены в защищённых переменных и защита от случайного тега, потому что
  публикация в Marketplace необратима, в отличие от Release внутри проекта.
- **Воспроизводимая упаковка обеих сторон.** Сейчас два прогона дают `.zip` и
  `.vsix` одного размера с разными SHA-256: в архивы попадают времена файлов.
  Из-за этого хеши артефактов на GitHub и в GitLab не совпадают, а полный
  перезапуск пайплайна на том же теге упирается в отказ публикации (сверка
  digest видит другие байты). Для Gradle это две строки
  (`isPreserveFileTimestamps`, `isReproducibleFileOrder`), для `vsce` флага нет
  — понадобится перепаковка `.vsix` с нормализованными временами и порядком
  записей. Выигрыш: один и тот же файл на всех площадках, проверяемый
  пользователем по хешу.
- **Модуль `:contract` без зависимости от платформы.** Сейчас проверка снимка
  `rules.json` (`exportRules --check`) компилирует все исходники плагина и потому
  тянет дистрибутив IDE — из-за этого она живёт внутри `test:idea` (на обоих
  хостингах), а не в дешёвой стадии `contract`, где ей место. Подграф
  контракта платформы не касается (`ExportRules` → gson,
  `SmartAppContract` → `SmartAppRefKind`, у которого импортов нет), поэтому его
  можно вынести в отдельный Gradle-модуль и подключить как
  `implementation(project(":contract"))` — тем же механизмом, что уже работает
  для gson. Осторожность нужна с упаковкой: тесты идут по runtime-classpath, где
  классы есть всегда, а в собранном zip их может не оказаться — обязательна
  проверка состава архива и ручная установка.
